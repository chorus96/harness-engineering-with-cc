## Part 01 — 하네스란 무엇인가

### Chapter 01 · 왜 하네스인가
- 스스로 데이터를 지운 단일 에이전트
- 혼자 일하는 AI는 자기 실수를 못 본다
- 모델의 환경을 바꿨을 때 일어난 일들
- 병목은 능력이 아니라 구조다
- [하네스](#g-harness) = [around the model](#g-around-model)
- [하네스](#g-harness)에 대한 세 가지 오해

> 📎 **예제로 보기**
> - **병목은 구조다 / around the model** → [`ex-02-01-ab-comparison`](../ex-02-01-ab-comparison). 모델·프롬프트를 그대로 두고 **주변 구조(에이전트+스킬)만** 얹었을 때 산출물이 달라지는 것을 A/B로 실측 — "능력이 아니라 구조가 병목"이라는 1장 주장을 뒷받침하는 실험.
> - **혼자 일하는 AI는 자기 실수를 못 본다** → [`ex-02-02-my-first-harness`](../ex-02-02-my-first-harness)의 author↔reviewer 분리. 생성자와 별도의 검증자를 두어 "스스로 못 보는 실수"를 잡는 최소 구조.

### Chapter 02 · 30분 Quick Start
- [Step 1] 같은 프롬프트, 다른 산출물
- [Step 2] 30분 안에 2인 팀 만들기
- 자주 틀리는 세 가지

> 📎 **예제로 보기**
> - **[Step 1] 같은 프롬프트, 다른 산출물** → [`ex-02-01-ab-comparison`](../ex-02-01-ab-comparison). 동일한 한 줄 프롬프트(`claude code 사용 팁 정리해주세요`)를 맨몸(`non-harness/`) vs 하네스(`apply-harness/`)로 실행: 자유 형식 치트시트 1개 ↔ "상황→방법→예시→주의점" 표준 포맷 8편+인덱스. `index.html`에서 2단 비교.
> - **[Step 2] 30분 안에 2인 팀 만들기** → [`ex-02-02-my-first-harness`](../ex-02-02-my-first-harness). `commit-message` 스킬 1개 + `commit-msg-author`/`commit-msg-reviewer` 2 에이전트로 구성한 최소 하네스. 스테이지된 diff를 받아 Conventional Commits 메시지를 협업 생성.

- [가드레일](#g-guardrail) — 에이전트가 할 수 없는 것을 파일로 정하기

- 핵심 파일 읽기 — copy-editor.md
- 책 집필 하네스의 7개 에이전트 관계도
- 안티패턴

> 📎 **예제로 보기**
> - **가드레일 — 할 수 없는 것을 파일로** → [`ex-04-01-security-analyst`](../ex-04-01-security-analyst). 프론트매터 `tools: Read, Grep, Glob, Bash`에서 **`Write`/`Edit`를 의도적으로 제외**해 "읽기 전용"을 물리적으로 강제. Bash도 조회용으로만 쓰도록 규칙으로 재차 좁힘.
> - **프론트매터 다섯 필드** → 두 예제의 프론트매터 대비: `security-analyst.md`는 `model: sonnet` + `tools` 명시, `copy-editor.md`는 `tools` **미기재로 부모 도구 상속**(주석에 근거 기록). 필드를 넣고/빼는 선택이 그대로 권한이 됨.
> - **핵심 파일 읽기 — copy-editor.md** → [`ex-04-02-copy-editor`](../ex-04-02-copy-editor)의 `.claude/agents/copy-editor.md`가 본문 섹션 구조(핵심 역할·처리 범위·작업 원칙·입출력 프로토콜·에러 핸들링·협업·품질 자체 검증)를 완비. "무엇을 고치고(콜론·Bold 조사·오탈자 3종) 무엇은 안 건드리는지(예외 케이스)"로 경계를 명시.

- 안티패턴

> 📎 **예제로 보기**
> - **원리 1 — Description이 호출을 결정** → [`ex-05-05-separation-signals`](../ex-05-05-separation-signals)와 각 SKILL.md의 `description`("~를 언급하면 호출. 단, ~는 아니다" 식). 어떤 스킬이든 description이 트리거 판단의 근거임을 보여줌.
> - **원리 2 — Progressive Disclosure** → [`ex-05-06-domain-references`](../ex-05-06-domain-references). `sql-query/SKILL.md`는 본문 없이 라우터(조건부 링크)만 두고, 도메인 본문은 `references/{finance,inventory}.md`로 위임해 **필요할 때만 로드**. 호출 트레이스 2건으로 조건부 로드를 시각화.
> - **원리 3 — Why-First** → [`ex-05-11-with-without`](../ex-05-11-with-without)의 `csv-summary/SKILL.md`: "숫자 열만 통계를 낸다 — **왜냐하면** 문자열 열에 통계는 의미가 없기 때문" 처럼 규칙마다 이유를 병기. [`ex-05-09-context-savings`](../ex-05-09-context-savings)는 이유를 남기며 산문을 30%+ 가지치기.

> - **안티패턴** → [`ex-05-12-antipatterns`](../ex-05-12-antipatterns)(거대 SKILL.md/references 부재/이유 없는 규칙 3종 진단) + [`ex-05-08-generalization`](../ex-05-08-generalization)(오버피팅 vs 일반화 적용률 비교).

## 스킬(skill) 부연 설명

> 목차 5장 「[스킬](#g-skill) 설계의 기술」과 관련 항목을 처음 접하는 독자를 위해, **스킬이 무엇이고 어떻게 생겼는지**를 본 저장소 예제 기준으로 자세히 풀었습니다.

### 스킬이란 — 에이전트와의 차이

**스킬(skill)** 은 자연어 요청에 반응해 호출되는 **재사용 가능한 워크플로**입니다. [에이전트](#g-agent)가 "누가(역할·권한을 가진 일꾼)"라면, 스킬은 "무엇을 어떤 순서로(절차)"에 가깝습니다.

| 구분 | 에이전트(agent) | 스킬(skill) |
|---|---|---|
| 위치 | `.claude/agents/<이름>.md` | `.claude/skills/<이름>/SKILL.md` |
| 성격 | 역할·도구·모델이 고정된 **일꾼** | 여러 단계를 담은 **절차/레시피** |
| 트리거 | 오케스트레이터가 호출 | `description`에 걸린 **자연어 요청**이 직접 호출 |
| 예 | `commit-msg-author`, `security-analyst` | `commit-message`, `sql-query`, `csv-summary` |

### 파일 구조

스킬은 폴더 하나로 이루어지며, 본문(`SKILL.md`)에 더해 보조 파일을 둘 수 있습니다.

```
.claude/skills/<이름>/
├── SKILL.md            ← 프론트매터 + 본문(절차)   ← 항상 로드
├── references/         ← 도메인 상세 (조건부 로드)   예) sql-query
│   ├── finance.md
│   └── inventory.md
├── workflows/          ← 모드별 세부 절차           예) mini-multi-mode
│   └── 01-readme.md
└── bin/                ← 실제 실행 스크립트          예) csv-summary
    └── run.sh
```

- **`references/`** — SKILL.md 본문은 얇게 두고 상세는 여기로 위임해, **필요할 때만 로드**합니다([Progressive Disclosure](#g-progressive)). → [`ex-05-06-domain-references`](../ex-05-06-domain-references)
- **`bin/`** — 스킬이 말만 하는 게 아니라 **실제로 동작**하는 구현을 담습니다. → [`ex-05-11-with-without`](../ex-05-11-with-without)의 `csv-summary/bin/run.sh`(파이썬 stdlib로 CSV 통계 산출)
- **`workflows/`** — 하나의 스킬이 여러 모드를 가질 때 모드별 절차를 분리. → [`ex-05-10-book-writer-skill`](../ex-05-10-book-writer-skill)의 `mini-multi-mode`

#### 폴더 규약 vs 프레임워크 규약 — 무엇이 "정해진 규칙"인가

예제 폴더에 보이는 `run/`·`result/`·`fixtures/`·`_workspace/` 등은 **Claude Code가 정한 규칙이 아니라, 저장소 저자가 산출물을 종류별로 나눠 담으려고 붙인 임의의 폴더명**입니다. Claude Code가 실제로 자동 인식(디스커버리)하는 것은 `.claude/` 아래뿐입니다.

| 경로 | 누가 정했나 | 성격 | 강제성(본 저장소) |
|---|---|---|---|
| `.claude/agents/*.md`, `.claude/skills/*/SKILL.md` | **Claude Code 프레임워크** | 고정 규약 · 자동 디스커버리 대상 | 22개 예제 **전부** |
| `references/`, `bin/`, `workflows/` | SKILL.md가 가리키는 하위 관례 | SKILL.md 본문이 링크해야 도달 | 필요한 스킬만 |
| `_workspace/` | **해당 SKILL.md가 스스로 정함** | 그 스킬 안에서만 "약속된 출력 경로"(이름 바꾸면 바뀜) | 1개 예제 |
| `run/`, `result/`, `fixtures/`, `sample-*/` | **저장소 저자의 정리 관례** | 프레임워크가 요구·인식하지 않는 임의 이름 | 예제마다 제각각(`run/`은 8개뿐) |

- `run/checklist.md`, `run/dry-run-log.md`, `run/log_success.txt` 등은 **실행 로그·검증 메모를 담는 서랍**일 뿐, 다른 이름이어도 동작에 지장이 없습니다.
- 일부 예제에만 있고 이름·구성이 제각각이라는 점 자체가 "규칙이 아니라 관례"라는 증거입니다.
- 예외적으로 `_workspace/`는 `commit-message`·`pr-review-orchestrator` 같은 **SKILL.md 본문이 "출력은 `_workspace/…`에 쓴다"고 직접 명시**해, 그 스킬 안에서는 약속된 값으로 동작합니다 — 그래도 프레임워크 규칙이 아니라 **그 스킬 파일이 정한 규칙**입니다.

### 프론트매터 3필드

```yaml
---
name: commit-message
description: "스테이지된 변경을 바탕으로 커밋 메시지를 2인 팀으로 생성. '커밋 메시지' 요청 시 반드시 사용. 단, 이미 메시지가 있는 경우는 아니다."
allowed-tools: Bash Read Write
---
```

- **`name`** — 스킬 식별자.
- **`description`** — **호출 여부를 결정하는 가장 중요한 필드.** "무엇을·언제 쓰고, 무엇은 **아닌지**"까지 적을수록 오호출이 줄어듭니다(→ [원리 1](#g-description)).
- **`allowed-tools`** — 이 스킬이 쓸 수 있는 도구 화이트리스트. 에이전트의 `tools`처럼 [가드레일](#g-guardrail) 역할을 합니다.

### 스킬 설계 3원리 (5장 핵심)

1. **[Description이 호출을 결정한다](#g-description)** — 스킬이 안 불리는 1순위 원인은 description이 모호해서입니다. 트리거 키워드와 제외 조건을 명시합니다.
2. **[Progressive Disclosure 3단계](#g-progressive)** — ① 프론트매터(요약) → ② SKILL.md 본문(절차·라우팅) → ③ `references/`(도메인 상세). 앞 단계만으로 판단하고, 깊은 정보는 필요할 때만 펼쳐 [토큰](#g-token)을 아낍니다.
3. **[Why-First](#g-whyfirst)** — 규칙마다 "왜"를 붙입니다. 예) [`ex-05-11`](../ex-05-11-with-without) `csv-summary`: *"숫자 열만 통계를 낸다 — 왜냐하면 문자열 열에 통계는 의미가 없기 때문."*

#### Why-First 자세히 — 규칙보다 이유를 먼저

**Why-First** 는 스킬·에이전트에 규칙을 적을 때 **"무엇을 하라"보다 "왜 그래야 하는지"를 함께(혹은 먼저) 적는** 설계 습관입니다.

**왜 필요한가** — 모델은 규칙을 **문자 그대로가 아니라 의도를 이해해** 따를 때 더 잘 작동합니다. 이유가 없으면 규칙이 예상치 못한 상황을 만났을 때 어떻게 처리할지 알 수 없어, 잘못 적용하거나 무시합니다. 이유가 있으면 **규칙에 없는 경계 상황에서도 의도에 맞게 판단**합니다.

**이유 없는 규칙 vs Why-First**

| | 이유 없는 규칙 (❌) | Why-First (✅) |
|---|---|---|
| 예시 | "숫자 열만 통계를 낸다." | "숫자 열만 통계를 낸다 — **왜냐하면** 문자열 열에 평균·표준편차는 의미가 없기 때문." |
| 새 상황(예: 숫자처럼 보이는 ID 열) | 기계적으로 통계를 냄 | "의미 있는 수치인가?"를 되물어 ID엔 통계를 빼는 판단 가능 |

**저장소 예제 근거**

- [`ex-05-11-with-without`](../ex-05-11-with-without) `csv-summary/SKILL.md` — 규칙마다 "왜냐하면"을 병기: *"그룹 요청이면 GROUP BY 후 집계 — 왜냐하면 전체 평균은 부서 비교에 쓸 수 없기 때문."*
- [`ex-04-02-copy-editor`](../ex-04-02-copy-editor) — "수정한다/수정하지 않는다"를 **예외 케이스의 이유와 함께** 명시(`12:30`, 코드 블록은 콜론이 의미를 가지므로 건드리지 않음).
- [`ex-05-12-antipatterns`](../ex-05-12-antipatterns) — **"이유 없는 규칙"을 3대 안티패턴 중 하나**로 잡아 진단·심각도 라벨링. Why-First의 반례를 실측으로 보여줌.
- [`ex-05-09-context-savings`](../ex-05-09-context-savings) — 이유를 남기며 산문을 30%+ 가지치기. Why는 유지하되 군더더기만 제거.

**작성 팁**

- 규칙 옆에 `— 왜냐하면 …` 한 구절이면 충분. 장문 설명이 아니라 **핵심 근거 한 줄**.
- 금지 규칙("~하지 마라")일수록 이유가 중요 — 이유가 없으면 과잉 적용되기 쉽습니다.
- 단, 이유가 **컨텍스트를 늘리는 군더더기**가 되면 안 됩니다([토큰 경제](#g-token)). Why는 남기되 중복 설명은 `references/`로 위임하거나 잘라냅니다.

> 한 줄 정리: **규칙은 "무엇"이고 Why-First는 "왜"다.** "왜"가 있어야 모델이 규칙 밖 상황에서도 의도대로 움직인다.

### 저장소 예제로 보는 스킬의 세 유형

| 유형 | 하는 일 | 예제 |
|---|---|---|
| **오케스트레이션 스킬** | 여러 에이전트를 순차·병렬 호출하고 결과를 통합 | [`commit-message`](../ex-02-02-my-first-harness)(author→reviewer), [`pr-review-orchestrator`](../ex-06-12-pr-review-skill-md), [`code-review-team`](../ex-11-05-orchestrator-6phase) |
| **라우터 스킬** | 본문은 얇게, 요청을 조건부로 `references`에 분기 | [`sql-query`](../ex-05-06-domain-references)(매출→finance, 재고→inventory) |
| **실행 스킬** | `bin/`의 실제 스크립트로 산출물을 직접 생성 | [`csv-summary`](../ex-05-11-with-without)(CSV 통계 요약) |

### 스킬 검증과 안티패턴

- **With/Without 검증** — 스킬이 정말 효과가 있는지 같은 작업을 스킬 유무로 실측 비교. → [`ex-05-11-with-without`](../ex-05-11-with-without)(`pass_rate`·`duration_ms`·`total_tokens` 3축).
- **안티패턴 3종** — ① 거대 SKILL.md(모든 걸 본문에), ② `references` 부재(도메인 분기를 본문에 욱여넣음), ③ 이유 없는 규칙(Why 누락). → [`ex-05-12-antipatterns`](../ex-05-12-antipatterns)가 이 3종을 진단·심각도 라벨링.

## 워크플로(workflow) 부연 설명

> 목차 11~14장 실전편의 「워크플로」 절과 [스킬](#g-skill)의 `workflows/` 폴더를 처음 접하는 독자를 위해, **워크플로가 무엇이고 파일에서 어떻게 표현되는지**를 본 저장소 예제 기준으로 정리했습니다.

### 워크플로란

**워크플로(workflow)** 는 작업을 끝내기 위한 **정해진 단계의 순서**입니다. 하네스에서 워크플로는 사람의 머릿속이 아니라 **파일(SKILL.md·에이전트 정의)에 명시**되어, 매번 같은 순서로 재현·재실행됩니다. 크게 두 곳에 나타납니다.

1. **[스킬](#g-skill) 본문(SKILL.md)의 절차** — 보통 `Phase 0 → 1 → 2 …` 시퀀스로 기술.
2. **`workflows/` 폴더** — 하나의 스킬이 여러 모드를 가질 때 모드별 절차를 파일로 분리.

### ① SKILL.md 안의 워크플로 — Phase 시퀀스

오케스트레이션 스킬은 본문을 **번호가 매겨진 단계(Phase)** 로 씁니다. 각 Phase는 "무엇을 하고 → 무엇을 남기는지"가 분명합니다.

- [`ex-06-12-pr-review-skill-md`](../ex-06-12-pr-review-skill-md) `pr-review-orchestrator/SKILL.md`
  - **Phase 0 사전 조건** (변경 파일 확인, 40개 초과 시 범위 분할)
  - **Phase 1 팀 생성** ([TeamCreate](#g-teamcreate) + 팀원 4인)
  - **Phase 2 작업 큐 배치** ([TaskCreate](#g-taskcreate), 통합 작업은 [depends_on](#g-dependson))
  - **Phase 3 팀원 간 메시지** ([SendMessage](#g-sendmessage), 리더 미경유)
  - **Phase 4 통합 게이트** (Critical·High 우선, 중복 병합 → `must-fix`/`should-fix`/`watch`)
  - **Phase 5 종료** (`shutdown_request` → [TeamDelete](#g-teamdelete), `_workspace/`는 보존)
  - **실패 처리** (팀원 실패 재시도·중단 조건까지 워크플로에 포함)
- [`ex-11-05-orchestrator-6phase`](../ex-11-05-orchestrator-6phase) `code-review-team/SKILL.md` — 같은 6 Phase를 **의사코드(TypeScript)** 로 표현: 입력 수집 → 팀 생성 → `TaskCreate`×4 → 팬아웃(리뷰어 3인 병렬) → [생성-검증](#g-pat-genver) 루프(최대 3회) → 통합·게시·정리.
- [`ex-02-02-my-first-harness`](../ex-02-02-my-first-harness) `commit-message/SKILL.md` — 가장 단순한 5단계 워크플로: 사전조건 체크 → author 호출 → reviewer 호출 → PASS/REDO 분기 → 재호출 2회 상한 후 종료.

### ② workflows/ 폴더 — 모드별 워크플로 분리

하나의 스킬이 여러 산출물 모드를 가질 때, 각 모드의 세부 절차를 `workflows/`로 나눕니다. → [`ex-05-10-book-writer-skill`](../ex-05-10-book-writer-skill)의 `mini-multi-mode`

```
.claude/skills/mini-multi-mode/
├── SKILL.md              ← 어떤 모드로 갈지 라우팅
└── workflows/
    ├── 01-readme.md      ← README 작성 절차
    ├── 02-changelog.md   ← CHANGELOG 작성 절차
    └── 03-pr-body.md     ← PR 본문 작성 절차
```
SKILL.md는 "요청이 README냐/CHANGELOG냐/PR 본문이냐"만 판단하고, 실제 단계는 해당 `workflows/*.md`로 위임합니다([Progressive Disclosure](#g-progressive)와 같은 원리).

### ③ 실전편 챕터의 「워크플로」 절이 가리키는 것

11~14장 각 팀 챕터의 「워크플로」 절은, 그 팀이 **입력을 받아 산출물까지 가는 Phase 흐름**을 뜻합니다. 본 저장소에서 대응하는 실물:

| 장 | 팀 | 워크플로 실물 |
|---|---|---|
| 11 코드 리뷰 | 4인 리뷰어 | [`ex-11-05`](../ex-11-05-orchestrator-6phase) 6 Phase + [`ex-11-06`](../ex-11-06-jwt-pr-bugs) 발견 매트릭스까지의 흐름 |
| 12 풀스택 | 8 에이전트 | [`ex-12-03`](../ex-12-03-team-8-agents) `01_phase_matrix.md`의 Phase 0~4(설계→구현→검증→통합) |
| 13 마이그레이션 | 의존성 분석 | [`ex-13-01`](../ex-13-01-dependency-mapper) 수집→import 추출→복잡도→위상정렬→`batches.json` |
| 14 디버깅/RCA | 사건 처리 | [`ex-14-10`](../ex-14-10-application-guide) 재현→가설→수정→[blameless](#g-blameless) 리뷰 |

### 워크플로 설계 체크포인트

좋은 워크플로가 파일에 반드시 담는 것들(예제 공통):

- **의존 순서** — 어떤 단계가 무엇을 기다리는가([depends_on](#g-dependson)). 통합은 앞선 작업 완료 후.
- **[생성-검증](#g-pat-genver) 루프와 상한** — 다시 만들되 무한 반복 금지(예: `MAX_RETRIES=3`, REDO 2회). → [`ex-08-15-max-retries-code`](../ex-08-15-max-retries-code)
- **실패 처리 / 종료** — 팀원 실패 시 재시도·중단 기준, 종료 시 팀 해체·산출물 보존.
- **재실행 가능성** — 같은 입력으로 같은 결과가 나오도록([재실행](#g-rerun) 트리거). → [`ex-11-05`](../ex-11-05-orchestrator-6phase)의 "리뷰 재실행".

### 스킬과 워크플로의 관계

한마디로 **[스킬](#g-skill)은 "그릇·진입점", 워크플로는 그 안에 담긴 "절차"** 입니다. 워크플로는 스킬의 구성 요소이지 별개 파일 종류가 아닙니다.

- **진입점 vs 내용** — 스킬은 `description`에 걸린 자연어 요청으로 **호출되는 단위**이고, 워크플로는 호출된 뒤 **실제로 실행되는 단계의 순서**입니다. 사용자는 "스킬"을 부르고, 그 안에서 "워크플로"가 돈다.
- **포함 관계** — 워크플로는 스킬 안에 산다. 두 자리에 나타납니다: ① SKILL.md 본문의 `Phase` 시퀀스(인라인), ② `workflows/` 폴더의 모드별 파일(분리).
- **1:1 vs 1:N** — 단순 스킬은 워크플로가 하나뿐입니다(예: [`commit-message`](../ex-02-02-my-first-harness)의 5단계). 여러 모드를 가진 스킬은 워크플로가 여럿이고, `description`/본문이 **어떤 워크플로로 갈지 라우팅**합니다(예: [`mini-multi-mode`](../ex-05-10-book-writer-skill) → `01-readme`/`02-changelog`/`03-pr-body`).
- **위임 방향** — 워크플로의 각 단계는 다시 [에이전트](#g-agent)를 호출하거나([`code-review-team`](../ex-11-05-orchestrator-6phase)의 Phase가 4 에이전트를 부름), [references](#g-progressive)를 조건부 로드합니다. 즉 **스킬 → 워크플로(단계) → 에이전트/references** 로 내려갑니다.

```
skill (진입점, description로 호출)
  └─ workflow (절차)
       ├─ Phase 0 …            ← SKILL.md 본문(인라인) 또는
       ├─ Phase 1 …               workflows/*.md(분리)
       └─ Phase n …
            └─ 각 단계가 agent 호출 · references 로드 · bin 실행
```

| 관점 | 스킬(skill) | 워크플로(workflow) |
|---|---|---|
| 무엇 | 재사용 단위(그릇·진입점) | 그 안의 단계 순서(절차) |
| 트리거 | `description` 자연어 요청 | 스킬이 호출된 뒤 내부에서 실행 |
| 파일 | `SKILL.md`(+`references/`,`bin/`) | SKILL.md 본문 `Phase` 또는 `workflows/*.md` |
| 개수 | 1 스킬 | 그 안에 1개 또는 N개(모드별) |
| 예제 | `commit-message`, `mini-multi-mode` | 5단계 / 6 Phase / 모드별 절차 |

> 요약: **스킬을 열면 워크플로가 있고, 워크플로의 각 단계가 에이전트·references·스크립트를 부린다.** 스킬은 "언제 부를지", 워크플로는 "부른 뒤 어떻게 진행할지"를 담당합니다.

#### Q. 워크플로는 스킬 없이 독립적으로 동작할 수 없나요?

**절차로서의 실행은 독립적으로 가능하지만, "자동 호출되는 하네스 단위"로는 [스킬](#g-skill)(또는 [에이전트](#g-agent))이라는 진입점이 필요합니다.**

- ✅ **독립 실행이 되는 경우** — 워크플로의 본질은 "단계의 순서"일 뿐이라, 스킬로 감싸지 않아도 다음처럼 돌아갑니다.
  - **스크립트 직접 실행**: `bash bin/run.sh`([`csv-summary`](../ex-05-11-with-without)), `python3 run/max_retries.py`([`ex-08-15`](../ex-08-15-max-retries-code)), `bash mock-mapper.sh`([`ex-13-01`](../ex-13-01-dependency-mapper)) — 셸에서 바로 실행.
  - **에이전트 안의 절차**: [`ex-13-01`](../ex-13-01-dependency-mapper) `dependency-mapper.md`는 6단계 절차를 **에이전트 정의 자체**에 담음(스킬 아님).
  - **문서(런북/체크리스트)**: `run/checklist.md` 같은 파일을 사람이나 Claude가 읽고 수동으로 따라감.
  - **[CLAUDE.md](#g-claudemd) 규칙**: 공통 절차를 규칙으로 적어두면 특정 스킬 없이도 세션 전반에 적용.
- ❌ **독립적이지 않은 경우** — Claude Code가 자동 인식(디스커버리)하는 경로는 `.claude/skills/`와 `.claude/agents/`뿐입니다. **`.claude/workflows/` 같은 자동 인식 경로는 없습니다.** 예제의 `workflows/` 폴더도 [`mini-multi-mode`](../ex-05-10-book-writer-skill) **안**에 있고 SKILL.md가 가리켜야만 도달합니다. 따라서 "이런 요청이 오면 알아서 이 절차를 돌려라"처럼 **자연어 트리거로 자동 호출**되려면, 트리거를 담을 `description`을 가진 스킬/에이전트가 있어야 합니다.

| 실행 방식 | 스킬 필요? |
|---|---|
| 셸에서 스크립트 직접 실행 | ❌ 불필요 |
| 에이전트 정의 안의 「절차」로 실행 | ❌ (에이전트가 대신 담음) |
| 문서를 읽고 수동으로 따라가기 | ❌ 불필요 |
| **자연어 요청으로 Claude가 자동 호출** | ✅ 스킬/에이전트 진입점 필요 |

> 한 줄 정리: **워크플로의 "실행"은 독립적일 수 있어도, 워크플로의 "자동 호출"은 스킬(또는 에이전트)에 얹혀야 한다.**

### 워크플로 vs 파이프라인

자주 헷갈리지만 **층위(altitude)가 다른** 개념입니다. **워크플로**는 "단계의 순서"라는 일반 개념(우산)이고, **[파이프라인](#g-pat-pipeline)** 은 그중 **한 가지 모양** — 에이전트를 일렬로 이어 앞 산출이 뒤 입력이 되는 [아키텍처 패턴](#g-pat-pipeline)입니다. 즉 **파이프라인 ⊂ 워크플로**(모든 파이프라인은 워크플로지만, 그 역은 아님).

| 관점 | 워크플로(workflow) | 파이프라인(pipeline) |
|---|---|---|
| 정체 | 절차 일반(단계의 순서) | 아키텍처 **패턴 1종**(순차 연결) |
| 층위 | "스킬이 어떻게 진행되나"(SKILL.md의 Phase 시퀀스) | "팀을 어떤 모양으로 짜나"(에이전트 위상) |
| 모양 | 순차·병렬·루프 등 **무엇이든** 가능 | **직선(순차)** 한 방향 |
| 병렬성 | 병렬 단계 포함 가능 | 원칙적으로 순차(앞이 끝나야 뒤) |
| 관계 | 상위(우산) 개념 | 워크플로의 한 인스턴스 |
| 예제 | [`ex-11-05`](../ex-11-05-orchestrator-6phase) 6 Phase(순차 + Phase 3 **팬아웃** 섞임) | [`ex-02-02`](../ex-02-02-my-first-harness) author→reviewer, [`ex-13-01`](../ex-13-01-dependency-mapper) 수집→추출→클러스터→위상정렬 |

**핵심 구분점** — [`ex-11-05`](../ex-11-05-orchestrator-6phase)의 워크플로는 6 Phase지만 **순수 파이프라인이 아닙니다.** Phase 3에서 리뷰어 3인이 동시에([팬아웃](#g-pat-fan)) 돌고 Phase 4에 [생성-검증](#g-pat-genver) 루프가 있죠 — 하나의 워크플로 안에 **파이프라인 구간 + 팬아웃 구간 + 루프 구간**이 섞여 있습니다. 반대로 [`ex-02-02`](../ex-02-02-my-first-harness)·[`ex-13-01`](../ex-13-01-dependency-mapper)은 단계가 일직선이라 **워크플로이면서 동시에 파이프라인**입니다.

> 비유: **워크플로 = 요리 순서 전반**(썰고·볶고·동시에 소스도 끓이고…), **파이프라인 = 그중 컨베이어벨트처럼 한 줄로 이어지는 방식.** 워크플로는 파이프라인·팬아웃·생성검증을 **담는 그릇**, 파이프라인은 그 안에 담기는 **한 가지 모양**입니다.

## 팀 도구(Team Tools) 부연 설명

> 목차 6장 「[오케스트레이터](#g-orchestrator)」의 [TeamCreate](#g-teamcreate)·[TaskCreate](#g-taskcreate)·[SendMessage](#g-sendmessage)·[TeamDelete](#g-teamdelete)를 **어떻게 구현하고 추가하는지**를, 본 저장소의 도구 분류 문서와 실험 기능 팁을 근거로 정리했습니다.

### 핵심: 팀 도구는 "구현"이 아니라 대부분 "활성화 + 선언"

5종 팀 도구는 여러분이 코드로 만드는 것이 아니라, **Claude Code의 실험적 기능 "에이전트 팀(Agent Teams)"이 제공**합니다. 따라서 "구현·추가"는 두 갈래입니다.

- **① 제공되는 5종** — *활성화하고 프론트매터에 선언*하면 됩니다(직접 구현 X).
- **② 의사 함수 4종** — *직접 구현*해야 합니다(제공되지 않음). → 아래 별도 표.

### 0단계 — 실험 기능 활성화

에이전트 팀은 기본 비활성입니다. 환경 변수로 켭니다. (출처: [`ex-02-01`의 팁 문서](../ex-02-01-ab-comparison/apply-harness/tips/agent-teams-experimental.md))

```bash
# 단일 세션
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude
# 셸 프로파일에 영구 설정
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

### 제공되는 5종 (선언만 하면 호출 가능)

출처: [`ex-11-05`의 도구 분류 문서](../ex-11-05-orchestrator-6phase/run/tool-classification.md).

| 도구 | 역할 | 호출 위치(예제) |
|---|---|---|
| **TeamCreate** | 팀(세션 객체) 부트스트랩 | Phase 1, 1회 |
| **AgentTool** | 팀원 에이전트 스폰(worktree 격리) | Phase 1, 4회 |
| **TaskCreate** | 공유 작업 큐에 작업 등록([depends_on](#g-dependson)로 순서) | Phase 2, 4회 |
| **SendMessage** | 팀원 간 직접 통신(리더 미경유) | Phase 3, 워커 `.md`에서 호출 |
| **TeamDelete** | 팀 해체(`_workspace/`는 보존) | Phase 5 |

### 추가 방법 — 3단계 선언

**1) 오케스트레이터 스킬 프론트매터에 `allowed-tools`로 선언** — [`ex-11-05`](../ex-11-05-orchestrator-6phase) `code-review-team/SKILL.md` 실물:

```yaml
---
name: code-review-team
allowed-tools: TeamCreate, AgentTool, TaskCreate, SendMessage, TeamDelete, Read, Write, Bash(gh pr diff, gh pr comment)
---
```

**2) 각 에이전트 프론트매터 `tools`에 필요한 팀 도구 선언** — 팀원끼리 통신하려면 그 에이전트의 `tools`에 `SendMessage`가 있어야 합니다([`ex-12-03`](../ex-12-03-team-8-agents) `api-designer.md`):

```yaml
---
name: api-designer
model: opus
tools: Read, Write, Grep, SendMessage
---
```

**3) 에이전트 `.md`에 「팀 통신 프로토콜」 섹션 작성** — 누구에게·언제·어떤 형식으로 메시지를 보낼지 규칙을 파일에 못박습니다. 메시지 형식을 JSON 스키마로 고정한 예([`ex-06-12`](../ex-06-12-pr-review-skill-md)):

```json
{ "type": "finding", "severity": "Critical|High|Medium|Low",
  "file": "path/to/file.ts", "line": 42,
  "claim": "문제를 주장하는 한 문장", "request": "상대가 확인할 질문" }
```

### 직접 구현해야 하는 것 — 의사 함수 4종

SKILL.md의 오케스트레이션 의사코드에는 팀 도구 외에 **구현자가 채워야 하는 헬퍼**가 섞여 있습니다. 이걸 팀 도구로 착각하면 안 됩니다(출처: [`ex-11-05` 도구 분류](../ex-11-05-orchestrator-6phase/run/tool-classification.md)).

| 의사 함수 | 하는 일 | 구현 힌트 |
|---|---|---|
| `parseDiff(diff)` | diff 텍스트 → 파일·hunk 메타 | `parse-diff` npm 패키지 또는 자체 정규식 |
| `waitForTeamCompletion(id, opts)` | 지정 작업 완료 대기 | TaskStatus 폴링 또는 이벤트 구독 |
| `mergeReports(reports, opts)` | N개 보고서를 우선순위로 통합 | 마크다운 파싱 + 정렬 |
| `$` (셸 헬퍼) | Bash 명령 실행 | `child_process.execSync` 또는 zx |

> SKILL.md를 다른 환경으로 복사할 때는 **이 4종을 먼저 채워야** 실제로 돌아갑니다.

### 생명주기와 주의점

```
TeamCreate → AgentTool×N → TaskCreate(depends_on) → SendMessage(peer) → TeamDelete
```

- **세션당 한 팀, 종료 시 정리 필수** — 세션을 재개(resume)해도 팀 구성은 복원되지 않으므로, 작업 후 반드시 [TeamDelete](#g-teamdelete)(또는 "clean up the team")로 정리합니다.
- **팀원 수 3~5명 권장** — 많으면 조율 오버헤드가 커집니다(6장 「292개 에이전트 사건」 참고).
- **독립 컨텍스트** — 팀원은 메인 대화를 자동 공유하지 않으므로 필요한 정보는 명시적으로 전달합니다.
- **실험적 기능** — 프로덕션 사용 전 검증하고, 지원 플랜·최소 버전은 [공식 문서](https://code.claude.com/docs/en/agent-teams)에서 확인합니다.

## 도메인(domain) 부연 설명

> 목차 5장 「도메인 분기형 references」와 7장 「Phase 1. 도메인 분석」을 처음 접하는 독자를 위해, **도메인이 무엇이고 하네스에서 어떤 역할을 하는지**를 저장소 예제 기준으로 정리했습니다.

### 도메인이란

**도메인(domain)** 은 이 하네스가 **다루는 문제 영역·주제**입니다. "무엇에 대한 일인가"를 가리킵니다. 저장소 예제로 보면:

| 예제 | 도메인 |
|---|---|
| [`ex-05-06`](../ex-05-06-domain-references) `sql-query` | 매출(finance) / 재고(inventory) |
| [`ex-04-01`](../ex-04-01-security-analyst) `security-analyst` | 보안 |
| [`ex-12-03`](../ex-12-03-team-8-agents) 8 에이전트 | 풀스택(로그인 기능) |
| [`ex-13-01`](../ex-13-01-dependency-mapper) `dependency-mapper` | 의존성 분석/마이그레이션 |

### 도메인의 역할 — 하네스 설계의 출발점

도메인은 하네스에서 네 가지를 결정합니다.

1. **팀 구성을 결정한다 (핵심)** — 메타스킬 [6단계 파이프라인](#g-pipeline6)의 **Phase 1이 「도메인 분석」**인 이유입니다. "하네스 구성해줘" 한 문장이 하는 일이 곧 **도메인 설명 → 전문가 [에이전트](#g-agent) 팀 + [스킬](#g-skill)** 로의 변환입니다. 보안 도메인이면 보안 감사자가, 풀스택이면 api/ui/db 설계자가 나옵니다.
2. **지식 분할(references)의 기준** — [`ex-05-06`](../ex-05-06-domain-references)처럼 SKILL.md 본문은 얇게 두고 **도메인별로 `references/finance.md`·`inventory.md`로 나눠** 필요한 도메인만 조건부 로드([Progressive Disclosure](#g-progressive)). 도메인이 곧 "지식을 나누는 칸막이".
3. **[Description](#g-description) 트리거의 어휘** — 트리거 키워드("Q4 매출", "재고 현황", "PR 리뷰")가 대부분 **도메인 용어**. 도메인 어휘가 정확할수록 호출 정확도가 오릅니다.
4. **에이전트 역할 경계** — 한 팀 안에서도 도메인 지식을 쪼개 배분. [`ex-07-13`](../ex-07-13-phase3-agent-5sections) `security-reviewer`가 "보안만 보고 스타일·테스트는 동료에게 위임"하는 것이 도메인 경계의 예.

> 한 줄 정리: **도메인은 "무엇에 대한 하네스인가"이고, 그 답이 팀 구성·지식 분할·트리거 어휘·역할 경계를 모두 결정한다.** 그래서 하네스를 짤 때 가장 먼저 하는 일이 「도메인 분석」입니다.

## 메타스킬 부연 설명

> 목차 7장 「[메타 하네스 스킬](#g-metaskill)과 [6단계 파이프라인](#g-pipeline6)」을 처음 접하는 독자를 위해, **메타스킬(메타 하네스)을 어떻게 구현하고 추가하는지**를 저장소 예제 기준으로 정리했습니다.

### 핵심: 메타스킬은 "파일을 쓰는 스킬"이다

[메타스킬](#g-metaskill)은 특별한 종류의 도구가 아니라 **일반 [스킬](#g-skill)** 입니다. 단지 산출물이 "문서"가 아니라 **다른 에이전트·스킬 파일**이라는 점이 다릅니다. 즉 `.claude/agents/*.md`와 `.claude/skills/*/SKILL.md`, 그리고 [`CLAUDE.md`](#g-claudemd) 포인터를 **Write로 생성**하는 스킬이 메타스킬입니다.

- **일반 스킬**: 입력 → (작업) → **산출물(문서·코드)**
- **메타스킬**: [도메인](#g-domain) 설명 → (6단계) → **하네스(에이전트+스킬+오케스트레이터 파일)**

> 그래서 프론트매터 `allowed-tools`에 **`Write`가 반드시 필요**합니다(파일을 만들어야 하므로).

### 0단계 — 형태

```
.claude/skills/harness/SKILL.md
---
name: harness
description: "도메인을 전문가 에이전트 팀으로 변환한다. '하네스 구성해줘', '팀 만들어줘' 같은 요청 시 사용."
allowed-tools: Read, Write, Bash
---
```

### 구현(추가) 방법 — 6단계 파이프라인을 SKILL.md에 담기

메타스킬의 본문은 아래 [6단계 워크플로](#g-pipeline6)를 절차로 기술합니다. 각 단계가 "무엇을 읽고 → 어떤 파일을 쓰는지"가 분명해야 합니다.

| Phase | 하는 일 | 산출/도구 |
|---|---|---|
| **1. 도메인 분석** | 무슨 분야·어떤 전문가·어떤 작업이 필요한지 질문을 정제 | (분석 메모) |
| **2. 팀 아키텍처 설계** | [6종 패턴](#g-pat-pipeline) 중 선택, 에이전트 수·모델·도구 경계 결정 | (설계표) |
| **3. 에이전트 생성** | 역할별 `.claude/agents/*.md`를 `Write` | 에이전트 파일 ×N |
| **4. 스킬 생성** | 공통 절차 `.claude/skills/*/SKILL.md`를 `Write` | 스킬 파일 ×M |
| **5. 오케스트레이션** | 호출 흐름을 스킬/`CLAUDE.md` 포인터로 등록 | `CLAUDE.md` |
| **6. 검증** | 파일 존재·도구 경계·트리거 어휘를 점검 | (체크리스트) |

### 산출물 구조 — 실물로 보기

[`ex-02-01`](../ex-02-01-ab-comparison)의 `apply-harness/`는 `/harness` 메타스킬이 **실제로 생성한 하네스**입니다(6단계의 결과물).

```
apply-harness/
├── CLAUDE.md                     ← Phase 5: 오케스트레이션 포인터(목적·폴더·작업 흐름·원칙)
└── .claude/
    ├── agents/                   ← Phase 3: 전문가 3인
    │   ├── tip-researcher.md
    │   ├── tip-writer.md
    │   └── tip-curator.md
    └── skills/                   ← Phase 4: 공통 스킬 3종
        ├── tip-collect/SKILL.md
        ├── tip-format/SKILL.md
        └── tip-publish/SKILL.md
```
CLAUDE.md의 「작업 흐름」 섹션이 "리서처→라이터→큐레이터"를 명시 — Phase 5가 만든 오케스트레이션 포인터입니다.

### 안전장치 — 메타스킬도 폭주할 수 있다

메타스킬은 파일을 **자동 생성**하므로 통제가 없으면 에이전트가 무한 증식합니다(6장 「292개 에이전트 사건」의 교훈).

- **에이전트 수 상한** — 팀당 3~5명 권장, 초과 시 분할.
- **재귀 깊이 제한** — 메타스킬이 또 메타스킬을 만드는 순환에 한계.
- **생성-후 검증 게이트(Phase 6)** — 파일이 실제로 존재하고 도구 경계가 지켜졌는지 확인 후 완료.
- **dry-run** — 실제 Write 전 계획만 출력해 검토.

### Phase 0·7 — 순환 구조로 진화

한 번 만들고 끝이 아니라, **기존 하네스 감사(Phase 0) → 생성/개선 → 사용 피드백 반영(Phase 7)** 으로 순환합니다. `revfactory/harness`가 말하는 **L3 Meta-Factory / 하네스 진화 메커니즘**이 이 루프입니다(→ [`하네스자료.md`](./하네스자료.md)).

> 한 줄 정리: **메타스킬 = `Write` 권한을 가진 스킬 + 6단계 파이프라인 + 폭주 안전장치.** "무엇을 만들지(도메인)"를 받아 "만드는 팀(에이전트+스킬+포인터)"을 파일로 찍어냅니다.

## 라우터(router) 부연 설명

> 목차 5장 「도메인 분기형 references」와 8장 「패턴 3. [전문가 풀 — 라우터 + 전문가](#g-pat-expert)」의 **라우터**를 처음 접하는 독자를 위해 정리했습니다.

### 라우터란 — "직접 일하지 않고, 어디로 보낼지만 정하는 것"

**[라우터](#g-router)** 는 들어온 요청을 보고 **알맞은 처리 대상으로 분기(dispatch)만 하는 얇은 층**입니다. 본체 작업은 하지 않고 "이 요청은 저기로" 안내만 합니다(네트워크 라우터가 패킷을 처리하지 않고 목적지로 넘기는 것과 같은 개념). 하네스에서는 두 층위로 나타납니다.

### 1. 스킬 본문이 라우터일 때 (references 분기)

[`ex-05-06`](../ex-05-06-domain-references) `sql-query/SKILL.md`가 전형적인 라우터입니다. 본문에 도메인 지식을 담지 않고 **조건부 링크만** 둡니다.

```
## 라우팅
- 매출 관련 요청이면 → references/finance.md
- 재고 관련 요청이면 → references/inventory.md
```

- 본문(라우터)은 **항상 로드**되지만 얇고, 실제 지식(`finance.md`·`inventory.md`)은 **필요할 때만** 펼칩니다 → [Progressive Disclosure](#g-progressive)로 [토큰](#g-token) 절약.
- SKILL.md 스스로 "메뉴판(라우터)"이라 부르고, 도메인 본문은 "레시피(references)"로 위임.

### 2. 팀에서 라우터일 때 (전문가 풀 패턴)

8장 [패턴 3 「전문가 풀 — 라우터 + 전문가」](#g-pat-expert)의 라우터입니다. 요청을 분류해 **알맞은 전문가 [에이전트](#g-agent)에게 배분**합니다.

- 라우터: "이건 보안 이슈 → security 에이전트, 이건 성능 → performance 에이전트"
- 전문가: 실제 판단·작업 수행

### 라우터의 역할 3가지

1. **분류(classify)** — 들어온 요청이 어떤 [도메인](#g-domain)·유형인지 판별.
2. **분기(dispatch)** — 판별 결과에 맞는 references/에이전트/워크플로 분기로 넘김.
3. **본체 없음(무발화)** — 스스로 답을 만들지 않음. 그래서 얇게 유지되고 컨텍스트를 아낌.

### 비슷한 개념과의 구분

| | 라우터 | [감독자](#g-pat-supervisor) | [오케스트레이터](#g-orchestrator) |
|---|---|---|---|
| 하는 일 | 정적 분기(어디로 보낼지) | 런타임 동적 분배 | 팀 생성·작업 배치·통합 |
| 판단 시점 | 요청 들어올 때 조건 매칭 | 실행 중 상황 따라 | 전체 라이프사이클 |
| 본체 작업 | 안 함 | 안 함(분배만) | 안 함(통합만) |

> 한 줄 정리: **라우터는 "요청을 읽고 알맞은 곳으로 넘기는 얇은 분기 층"** 이다. 스킬 본문에서는 references 분기로, 팀에서는 전문가 배분으로 나타나며, 공통점은 **자기가 일하지 않고 얇게 유지된다**는 것.

## 재시도 상한 · 에스컬레이션 부연 설명

> 목차 8장 「패턴 4. [생성-검증](#g-pat-genver)」과 7장 「안전장치 — 메타스킬도 폭주할 수 있다」에서 다루는 두 안전장치를, 저장소 예제 [`ex-08-15`](../ex-08-15-max-retries-code) 코드 기준으로 정리했습니다.

### 두 개념은 "생성-검증 루프의 안전장치" 한 쌍

에이전트가 만들고(generator) 검증자가 검사하는(verifier) [루프](#g-pat-genver)는 실패하면 다시 만듭니다. 계속 실패할 때를 대비한 두 장치입니다.

- **재시도 상한(retry cap)** = "몇 번까지만 다시 해라"는 **최대 횟수**.
- **에스컬레이션(escalation)** = 상한에 도달해도 통과 못 하면 **위(사람/상위 주체)로 넘기는 것**.

### 재시도 상한 — 무한 루프를 막는 브레이크

[`ex-08-15`](../ex-08-15-max-retries-code) `run/max_retries.py`의 실제 코드가 이 개념 그대로입니다.

```python
MAX_RETRIES = 3

def generate_with_retries(spec, generator, verifier):
    for attempt in range(MAX_RETRIES):     # ← 최대 3회
        artifact = generator.run(spec)
        result = verifier.run(artifact)
        if result.passed:
            return artifact                # 통과하면 즉시 종료
    return f"escalated: {MAX_RETRIES}회 실패, 수동 개입 필요"   # ← 에스컬레이션
```

- **왜 필요한가** — LLM 자동 루프는 실패해도 얼마든지 계속 돌 수 있어 **[토큰](#g-token)·시간·비용이 폭주**합니다. 상한은 "여기서 멈춘다"는 물리적 한계입니다.
- 예제에서 `success` 시나리오는 2회차에 통과해 빠져나오고, `fail` 시나리오는 3회를 다 쓰고도 실패합니다.

### 에스컬레이션 — 실패를 "조용히" 두지 않는 것

상한에 도달해도 통과 못 하면, 핵심은 **그냥 실패로 끝내지 않고 명시적으로 넘긴다**는 것입니다. 위 코드가 마지막에 `"escalated: … 수동 개입 필요"`를 반환하는 부분이 그것입니다.

- **왜 필요한가** — 상한만 있고 에스컬레이션이 없으면 루프는 멈추지만 **아무도 실패를 모르는** 상태(silent failure)가 됩니다. 에스컬레이션은 "자동으로 못 했으니 사람이 봐 달라"는 **신호이자 인계**입니다.
- 넘기는 대상은 사람(수동 검토)·상위 에이전트·별도 큐(`manual-queue`) 등 상황에 따라 다릅니다.

### 저장소의 다른 사례

| 예제 | 재시도 상한 | 에스컬레이션 |
|---|---|---|
| [`ex-08-15`](../ex-08-15-max-retries-code) | `MAX_RETRIES=3` | `"escalated: 수동 개입 필요"` 반환 |
| [`ex-02-02`](../ex-02-02-my-first-harness) | author↔reviewer **REDO 2회** | "자동 승인 한계 도달 — 수동 검토 권장" 경고 + 마지막 초안 반환 |
| [`ex-11-04`](../ex-11-04-three-frontmatter) | `refactorer` 생성-검증 **3회** | 상한 후 미해결 항목 보고 |
| [`ex-13-01`](../ex-13-01-dependency-mapper) | 파싱 실패 파일 | `manual-queue`에 기록(사람이 처리) |

> 한 줄 정리: **재시도 상한은 "언제 멈출지"(브레이크), 에스컬레이션은 "멈춘 뒤 누구에게 넘길지"(인계).** 둘이 짝을 이뤄야 자동 루프가 폭주하지도, 실패를 숨기지도 않습니다.

## Post-mortem 부연 설명

> 목차 14장 「디버깅 / [RCA](#g-rca) 팀」의 마무리 단계인 **포스트모템**을, 저장소 예제 [`ex-14-10`](../ex-14-10-application-guide)의 `reviewer.md` 기준으로 정리했습니다.

### Post-mortem이란

**[포스트모템](#g-postmortem)(post-mortem, 사후 분석)** 은 장애·버그·사고가 **처리된 뒤**, 무슨 일이 있었고 왜 일어났으며 어떻게 다시 안 나게 할지를 문서로 정리하는 활동입니다. 원래 "부검(사후 검시)"에서 온 말로, IT에서는 "사건 회고"에 가깝습니다.

- **[RCA](#g-rca)** 가 **"왜 터졌나"** 를 파는 것이라면,
- **Post-mortem** 은 그 결과까지 포함해 **"무슨 일이었나 + 왜 + 앞으로 어떻게"** 를 정리하는 **더 넓은 마무리 단계**입니다.

### 핵심은 blameless(무비난)

가장 중요한 원칙은 **개인 책임을 묻지 않는([blameless](#g-blameless))** 태도입니다. "누가 잘못했나"가 아니라 **"어떤 구조·프로세스가 이 실수를 허용했나"** 에 집중합니다. 사람을 탓하면 다음부터 사고를 숨기게 되어 오히려 재발을 키우기 때문입니다.

### 저장소에서 보기 — `ex-14-10`의 `reviewer`

14장 디버깅/RCA 팀의 Post-mortem 단계는 [`ex-14-10-application-guide`](../ex-14-10-application-guide)의 `reviewer.md`가 실물로 보여줍니다.

```yaml
---
name: reviewer
description: Post-mortem 전용. 사건 처리 산출물 전체를 blameless 관점으로 검토하고 구조 개선 제안을 작성.
model: opus
tools: Read        # ← 읽기 전용
---
```

- **읽기 전용(`tools: Read` 단독)** — 사건 처리 산출물(재현 스크립트·가설·수정 패치·완료 체크리스트·타임라인·알람 히스토리)을 **모두 읽되 고치지는 않습니다.** 부검하는 사람이 시신을 되살리지 않듯, 리뷰어는 사건을 재현·수정하지 않고 **검토와 개선 제안만** 합니다([가드레일](#g-guardrail)로 역할 고정).
- **산출물** — blameless 관점의 **구조 개선 제안**. "이 코드가 나빴다"가 아니라 "이런 알람이 있었다면 더 빨리 잡았을 것" 같은 방향.

### Post-mortem이 담는 것 (일반 구성)

| 항목 | 내용 |
|---|---|
| 타임라인 | 언제 발생·감지·복구했나 |
| 영향 | 무엇이 얼마나 영향받았나 |
| 근본 원인 | [RCA](#g-rca) 결과 |
| 대응 경과 | 어떻게 처리했나 |
| 재발 방지 | 구조·프로세스 개선 액션(가장 중요) |

> 한 줄 정리: **Post-mortem은 "사건이 끝난 뒤, 사람을 탓하지 않고(blameless) 구조를 고치는 회고"** 다. 14장 RCA 팀에서는 **읽기 전용 `reviewer`가 산출물을 검토해 재발 방지 개선안만 내놓는** 마지막 단계로 구현된다.

### 큰 개념

<a id="g-harness"></a>
- **하네스(harness)** — 말·낙하산의 "마구·장비"에서 온 말로, 여기서는 **AI 모델을 감싸는 작업 환경 전체**를 뜻합니다. 프롬프트 한 번을 잘 던지는 것이 아니라, 모델이 일하기 전에 에이전트·스킬·규칙·도구 경계를 미리 세팅해두는 구조를 가리킵니다.

<a id="g-around-model"></a>
- **around the model** — "모델 자체(성능)를 바꾸는 것이 아니라 모델 **주변**을 설계한다"는 하네스의 슬로건. 병목이 모델 능력이 아니라 그것을 둘러싼 구조에 있다는 관점입니다.

<a id="g-agent"></a>
- **에이전트(agent)** — 특정 역할·도구·모델로 **고정된 작업 단위**. Claude Code에서는 `.claude/agents/<이름>.md` 파일 하나가 에이전트 하나이며, 파일이 없으면 그 에이전트는 "존재하지 않는" 것으로 취급됩니다.

<a id="g-skill"></a>
- **스킬(skill)** — 자연어 트리거로 호출되는 **재사용 워크플로**. `.claude/skills/<이름>/SKILL.md`에 정의하며, 여러 단계를 담은 절차나 여러 에이전트를 순차·병렬로 호출하는 흐름을 담습니다. → 📖 자세히: [스킬 부연 설명](#스킬skill-부연-설명)

<a id="g-orchestrator"></a>
- **오케스트레이터(orchestrator)** — 여러 에이전트로 이루어진 **팀을 지휘하는 주체**. 직접 결과물을 쓰기보다 팀을 만들고, 작업을 배치하고, 결과를 통합하는 "지휘자" 역할을 합니다.

<a id="g-subagent"></a>
- **서브에이전트(subagent)** — 상위 에이전트가 필요할 때 **직접 호출하는 하위 에이전트**. 팀(공유 큐·상호 통신)에 편입되지 않고 단발성으로 불려 쓰이는 실행 모드입니다.

<a id="g-hybrid"></a>
- **하이브리드(hybrid)** — 팀 방식과 서브에이전트 방식을 **섞어 쓰는 실행 모드**.

<a id="g-domain"></a>
- **도메인(domain)** — 이 하네스가 **다루는 문제 영역·주제**("무엇에 대한 일인가"). 예) 보안, 코드 리뷰, 매출/재고 쿼리, 풀스택 로그인. **도메인이 팀 구성·지식 분할·트리거 어휘·역할 경계를 결정**하므로, 하네스 설계의 출발점(메타스킬 6단계 중 Phase 1 「도메인 분석」)입니다. → 📖 자세히: [도메인 부연 설명](#도메인domain-부연-설명)

<a id="g-workflow"></a>
- **워크플로(workflow)** — 작업을 끝내기 위한 **정해진 단계의 순서**. 하네스에서는 SKILL.md의 `Phase 0→1→2…` 시퀀스나 `workflows/` 폴더로 파일에 명시되어 매번 재현·재실행됩니다. → 📖 자세히: [워크플로 부연 설명](#워크플로workflow-부연-설명)

### 에이전트·스킬 파일 구성

<a id="g-frontmatter"></a>

- **Why-First 원칙** — 규칙마다 **"왜 그렇게 해야 하는지" 이유를 함께 적는** 설계 습관. 이유가 있으면 모델이 규칙의 의도를 이해해 예외 상황에서도 올바르게 판단합니다. → 📖 자세히: [Why-First 자세히](#why-first-자세히--규칙보다-이유를-먼저)

### 오케스트레이션·팀 도구

<a id="g-teamcreate"></a>
- **TeamCreate** — **팀(세션 객체)을 생성**하는 도구. 팀은 고정 상수가 아니라 세션 동안만 존재하는 실행 단위입니다. → 📖 자세히: [팀 도구 부연 설명](#팀-도구team-tools-부연-설명)

<a id="g-taskcreate"></a>
- **TaskCreate** — 팀의 **공유 작업 큐에 작업을 등록**하는 도구.

<a id="g-dependson"></a>
- **depends_on** — 한 작업이 **다른 작업들의 완료를 선행 조건으로 요구**하는 의존 관계 선언. 예: 통합 작업은 앞선 3개 리뷰가 끝나야 시작.

<a id="g-sendmessage"></a>
- **SendMessage** — **에이전트끼리 리더를 거치지 않고 직접 주고받는 메시지 채널**(peer-to-peer). 팀원 간 발견 사항 공유에 쓰입니다. → 📖 자세히: [팀 도구 부연 설명](#팀-도구team-tools-부연-설명)

<a id="g-teamdelete"></a>
- **TeamDelete** — 작업이 끝난 **팀을 해체·정리**하는 도구. "세션당 한 팀, 종료 시 shutdown 필수"가 권장 규칙입니다.

<a id="g-p2p"></a>
- **peer-to-peer(P2P, 피어 투 피어)** — 중앙(리더)을 거치지 않고 **동료끼리 직접 통신**하는 방식. 팀원(피어)들이 서로 메시지를 주고받는 구조를 가리킵니다.

<a id="g-eventloop"></a>
- **이벤트 루프(event loop)** — 리더가 직접 일하지 않고 **들어오는 이벤트에 반응해 조율만 하는 실행 모델**. "리더는 이벤트 루프, 팀원은 피어"라는 표현이 여기서 나옵니다.

<a id="g-protocol"></a>
- **팀 통신 프로토콜(team communication protocol)** — 에이전트 파일에 명시하는, **팀원과 어떤 형식·규칙으로 메시지를 주고받을지** 정한 약속(예: JSON 메시지 스키마).

### 메타스킬과 파이프라인

<a id="g-metaskill"></a>
- **메타스킬 / 메타 하네스(meta-skill / meta-harness)** — **하네스를 만들어내는 하네스**. 새 작업이 주어지면 도메인을 분석하고 팀·에이전트·스킬을 스스로 설계해 산출하는 상위 스킬입니다. → 📖 자세히: [메타스킬 부연 설명](#메타스킬-부연-설명)

<a id="g-pipeline6"></a>
- **6단계 파이프라인** — 메타스킬이 하네스를 만들어내는 절차: **① 도메인 분석 → ② 팀 아키텍처 설계 → ③·④ 에이전트·스킬 생성 → ⑤ 오케스트레이션 → ⑥ 검증** (앞뒤로 Phase 0·7의 순환 구조).

<a id="g-phase"></a>
- **Phase(페이즈)** — 워크플로를 구성하는 **단계**. 각 페이즈마다 활성화되는 에이전트와 목적이 달라집니다.

[↑ 목차](#하네스엔지니어링-with-claude-code--목차)

### 아키텍처 패턴 (6종)

<a id="g-pat-pipeline"></a>
- **파이프라인(pipeline)** — 에이전트를 **일렬로 이어** 앞 결과가 뒤의 입력이 되는 패턴. 순서 자체가 의미를 만듭니다.

<a id="g-pat-fan"></a>
- **팬아웃·팬인(fan-out / fan-in)** — **같은 입력을 여러 에이전트에 병렬로 뿌리고(fan-out)** 결과를 **하나로 모으는(fan-in)** 패턴. 같은 대상을 여러 관점으로 동시에 검토할 때 씁니다.

<a id="g-pat-expert"></a>
- **전문가 풀(expert pool)** — **[라우터](#g-router)가 요청을 분류해 알맞은 전문가 에이전트에게 배분**하는 패턴.

<a id="g-router"></a>
- **라우터(router)** — 들어온 요청을 보고 **알맞은 처리 대상으로 분기(dispatch)만 하는 얇은 층**. 본체 작업은 하지 않아 얇게 유지되고 컨텍스트를 아낍니다. 스킬 본문에서는 `references` 분기로(예: `sql-query`), 팀에서는 전문가 배분으로 나타납니다. → 📖 자세히: [라우터 부연 설명](#라우터router-부연-설명)

<a id="g-pat-genver"></a>
- **생성-검증(generator-verifier)** — 한 에이전트가 **만들고(generator)** 다른 에이전트가 **검사하며(verifier)**, 통과할 때까지 다시 만드는 루프. 보통 [재시도 상한과 에스컬레이션](#g-retry)을 둡니다.

<a id="g-retry"></a>
- **재시도 상한 / 에스컬레이션(retry cap / escalation)** — 생성-검증 루프의 안전장치 한 쌍. **재시도 상한**은 "몇 번까지만 다시 해라"는 최대 횟수(무한 루프·비용 폭주 방지), **에스컬레이션**은 상한에 도달해도 통과 못 하면 실패를 숨기지 않고 **사람/상위 주체로 넘기는 것**. → 📖 자세히: [재시도 상한·에스컬레이션 부연 설명](#재시도-상한--에스컬레이션-부연-설명)

<a id="g-pat-supervisor"></a>
- **감독자(supervisor)** — **런타임에 작업을 동적으로 나눠 배분**하는 패턴. 미리 정한 순서가 아니라 상황에 따라 분배가 달라집니다.

<a id="g-pat-hier"></a>
- **계층적 위임(hierarchical delegation)** — **총괄 → 팀장 → 실무자**로 이어지는 다층 구조. 큰 작업을 계층적으로 쪼개 내려보냅니다.

[↑ 목차](#하네스엔지니어링-with-claude-code--목차)

### 운영·진화

<a id="g-drift"></a>
- **drift(드리프트)** — 문서·설정과 실제 동작이 **시간이 지나며 서로 어긋나는 현상**. 변경 이력을 물리적 증거로 남겨 이를 방지합니다.

<a id="g-rerun"></a>
- **재실행 / 부분 재실행(re-run / partial re-run)** — 하네스 **전체를 다시 돌리거나, 바뀐 일부 단계만 골라 다시 돌리는** 것.

<a id="g-adr"></a>
- **ADR(Architecture Decision Record)** — **아키텍처 결정 기록**. 왜 이런 구조를 택했는지 결정과 근거를 문서로 남기는 관행입니다.

<a id="g-btd"></a>
- **Build to Delete** — 처음부터 **버릴 것을 전제로 가볍게 만드는** 접근. 하네스를 영구 자산이 아니라 필요하면 갈아치우는 것으로 다룹니다.

[↑ 목차](#하네스엔지니어링-with-claude-code--목차)

### 실전편 용어

<a id="g-pr"></a>
- **PR 리뷰(Pull Request review)** — 코드 변경 요청(PR)의 **diff를 검토**하는 작업. 정적 분석·보안·테스트 영향 등을 여러 리뷰어가 나눠 봅니다.

<a id="g-diff"></a>
- **diff(디프)** — 코드의 **변경 전후 차이**. 리뷰·분석의 기본 입력 단위입니다.

<a id="g-migration"></a>
- **마이그레이션(migration) / 배치(batch)** — 레거시 코드·테스트를 **새 방식으로 옮기는 작업**(마이그레이션)과, 그 대상을 의존 관계에 따라 **묶은 실행 단위**(배치).

<a id="g-rca"></a>
- **RCA(Root Cause Analysis, 근본 원인 분석)** — 버그·장애의 **표면 증상이 아닌 근본 원인**을 찾아내는 분석. "로컬에선 되는데 왜 안 되나" 같은 재현·원인 규명 작업이 여기에 해당합니다.

<a id="g-blameless"></a>
- **blameless(무비난) post-mortem** — 사후 분석에서 **개인 책임을 묻지 않고 구조·프로세스 개선에 집중**하는 방식.

<a id="g-postmortem"></a>
- **포스트모템(post-mortem, 사후 분석)** — 장애·버그·사고가 **처리된 뒤** 무슨 일이었나 + 왜 + 앞으로 어떻게를 정리하는 회고. [RCA](#g-rca)(원인 규명)를 포함하는 더 넓은 마무리 단계로, **[blameless](#g-blameless)(무비난)** 태도로 구조 개선에 집중합니다. → 📖 자세히: [Post-mortem 부연 설명](#post-mortem-부연-설명)

<a id="g-token"></a>
- **토큰 경제(token economy)** — LLM이 처리하는 **토큰(비용·컨텍스트 한도)을 자원으로 보고 아껴 쓰는 관점**. 무엇을 항상 로드하고 무엇을 필요할 때만 불러올지 설계합니다.

<a id="g-refarch"></a>
- **레퍼런스 아키텍처(reference architecture)** — 실전에서 그대로 참고할 수 있는 **표준 구조 청사진**.
