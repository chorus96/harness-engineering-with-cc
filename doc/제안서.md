# 제안서 — AMD FPGA 대상 RTL 개발 하네스 구축

> **문서 성격**: 본 문서는 《하네스 엔지니어링 with 클로드 코드》의 개념과 본 저장소 예제 패턴을 **AMD(Xilinx) FPGA RTL 개발 도메인**에 매핑한 **구축 제안서**입니다.
> **주의**: 본문의 비용·기간·정량 효과 수치는 특정 조직에 검증된 값이 아니라 **가정에 기반한 예시(illustrative estimate)** 입니다. 실제 도입 시 조직 규모·기존 EDA 환경·보안 정책에 맞춰 재산정해야 합니다.
> **범위 한정**: 하네스는 EDA 툴(Vivado/Vitis 등)을 **대체하지 않고 오케스트레이션**합니다. 최종 사인오프(합성/타이밍/기능 서명)는 기존 툴과 사람이 담당합니다.

---

## 1. 요약 (Executive Summary)

AMD FPGA용 RTL 개발은 **요구 정의 → 조사 → 설계 → 구현(RTL) → 검증 → 리뷰 → 배포(비트스트림) → 모니터링** 으로 이어지는 반복 루프이며, 각 단계가 서로 다른 전문성(마이크로아키텍처, SystemVerilog/VHDL, UVM 검증, CDC/타이밍, XDC 제약)을 요구합니다. 현재는 이 전문성이 개인에게 흩어져 있어 **재현성·일관성·리드타임**에 병목이 생깁니다.

본 제안은 Claude Code 기반 **하네스**를 구축해, RTL 개발 작업 환경 자체를 **전문 에이전트 팀 + 스킬 + 오케스트레이터**로 표준화합니다. 핵심 명제는 이 책의 것과 같습니다 — **"모델이 아니라 모델을 감싼 하네스가 결과를 결정한다."** 즉, EDA 툴과 사내 설계 규칙을 하네스로 감싸 **반복 가능한 파이프라인**으로 만드는 것이 목표입니다.

## 2. 배경과 대상 도메인

### 2.1 AMD FPGA RTL 개발 스택 (전제)

| 계층 | 대표 요소 |
|---|---|
| 디바이스/제품군 | AMD UltraScale+, Versal(ACAP) 등 |
| 설계 언어 | SystemVerilog / Verilog / VHDL |
| 합성·구현 툴 | AMD Vivado (batch: `vivado -mode batch -source *.tcl`), Vitis / Vitis HLS |
| 시뮬레이션 | Vivado xsim, 서드파티 시뮬레이터, Verilator(오픈소스 린트/시뮬) |
| 정적 검증 | 린트, CDC(클록 도메인 크로싱), 합성성(synthesizability) 체크 |
| 정형 검증 | 프로퍼티/등가성 검증(가용 시) |
| 제약 | XDC(타이밍·핀·클록), 타이밍 클로저(STA) |
| 검증 방법론 | UVM / cocotb, 커버리지, 리그레션 |

> 본 하네스는 위 툴을 **CLI/Tcl 배치로 호출**해 결과 로그를 파싱하고, 에이전트가 그 결과를 근거로 판단하도록 설계합니다.

### 2.2 왜 지금 하네스인가 (본 저장소 근거)

이 저장소는 소프트웨어 도메인에서 하네스가 산출물의 품질·구조·재현성을 어떻게 바꾸는지 예제로 보여줍니다. RTL 개발은 그 특성상 하네스 효과가 **더 큰** 도메인입니다.

- **툴 체인이 이미 CLI/스크립트 친화적** → 에이전트가 `Bash`로 툴을 구동하고 로그를 파싱하기 쉽습니다(참고: [`ex-13-01`](../ex-13-01-dependency-mapper)의 `mock/live` 실행, [`ex-05-11`](../ex-05-11-with-without)의 `bin/run.sh` 실측 스킬).
- **검증 비용이 크고 반복적** → 생성-검증 루프와 재시도 상한이 곧바로 시간 절감으로 연결됩니다(참고: [`ex-08-15`](../ex-08-15-max-retries-code) `MAX_RETRIES`).
- **리뷰가 다관점** → 린트/CDC/타이밍/설계를 병렬로 보는 팬아웃·팬인이 자연스럽게 맞습니다(참고: 11장 코드 리뷰 팀 [`ex-11-04`](../ex-11-04-three-frontmatter)/[`ex-11-06`](../ex-11-06-jwt-pr-bugs)).

## 3. 구축 필요성 (As-Is 문제 정의)

| 영역 | 현재(As-Is) 문제 | 하네스가 겨냥하는 지점 |
|---|---|---|
| 조사/사양 | 데이터시트·UG(User Guide)·기존 IP를 개인이 산발적으로 조사, 근거가 문서에 남지 않음 | `references/`에 디바이스·IP 지식을 고정, 조사 결과를 산출물로 남김 |
| 설계 | 마이크로아키텍처 결정의 근거·대안이 기록되지 않아 리뷰·재사용이 어려움 | 설계 에이전트가 결정+근거(ADR)를 파일로 산출 |
| 구현(RTL) | 코딩 스타일·리셋/CDC 규칙이 사람마다 다름, 린트 위반 반복 | 스타일·규칙을 스킬(Why-First)로 고정, 커밋 전 자동 린트 |
| 검증 | 테스트벤치·커버리지 작성이 병목, 리그레션 실패 분류(triage)에 시간 소모 | 검증 에이전트가 TB 초안·리그레션·실패 1차 분류 수행 |
| 타이밍/제약 | XDC·타이밍 클로저가 후반부에 몰려 재작업 발생 | 타이밍 에이전트가 조기·반복 점검 |
| 지식 전수 | 시니어 의존도가 높고 온보딩이 오래 걸림 | 하네스가 "실행 가능한 규칙"으로 지식을 코드화 |

> 핵심: **문제는 개별 엔지니어의 역량이 아니라, 전문성이 파일로 고정되지 않아 매번 재현되지 않는 구조**입니다(1장 "병목은 능력이 아니라 구조" 대응).

## 4. 구축 방법 및 예상 하네스 구성 (To-Be)

### 4.1 전체 구조

본 저장소의 3요소 구조를 그대로 따릅니다: **에이전트(`.claude/agents/`) + 스킬(`.claude/skills/`) + 오케스트레이터/규칙(`CLAUDE.md`)**. 여기에 RTL 도메인 지식을 `references/`로 분기합니다.

```
rtl-harness/
├── CLAUDE.md                       # 프로젝트 규칙·오케스트레이션 포인터·코딩 컨벤션
├── .claude/
│   ├── agents/                     # 전문 에이전트(역할·모델·도구 경계 고정)
│   │   ├── spec-researcher.md
│   │   ├── microarch-designer.md
│   │   ├── rtl-coder.md
│   │   ├── testbench-engineer.md
│   │   ├── lint-checker.md
│   │   ├── cdc-analyst.md
│   │   ├── timing-constraints.md
│   │   ├── synthesis-runner.md
│   │   ├── verification-reviewer.md
│   │   └── rca-debugger.md
│   └── skills/                     # 재사용 워크플로(스킬)
│       ├── rtl-review-team/SKILL.md         # 다관점 리뷰 오케스트레이션
│       ├── rtl-generate-verify/SKILL.md     # 생성-검증 루프(재시도 상한)
│       ├── run-lint/{SKILL.md,bin/run.sh}   # 실행 스킬(Verilator/Vivado 린트)
│       ├── run-sim/{SKILL.md,bin/run.sh}    # 시뮬레이션 배치
│       ├── run-synth/{SKILL.md,bin/run.sh}  # 합성·타이밍 배치(Vivado Tcl)
│       └── device-refs/                     # 도메인 분기 references(라우터)
│           ├── SKILL.md
│           └── references/
│               ├── ultrascale-plus.md
│               └── versal.md
├── rtl/                            # 설계 소스(SystemVerilog/VHDL)
├── tb/                            # 테스트벤치·UVM/cocotb
├── constraints/                   # XDC
└── run/                           # 실행 로그·리포트(관례 폴더)
```

> `run/`·`rtl/`·`tb/` 같은 폴더는 프레임워크 규칙이 아니라 **저장소 관례**입니다(본 저장소 [`목차.md`](./목차.md)의 "폴더 규약 vs 프레임워크 규약" 참고). Claude Code가 자동 인식하는 것은 `.claude/` 뿐입니다.

### 4.2 에이전트 구성 (역할·모델·도구 경계)

도구 경계로 역할을 물리적으로 고정합니다(참고: [`ex-04-01`](../ex-04-01-security-analyst) 읽기 전용, [`ex-11-04`](../ex-11-04-three-frontmatter) 도구 경계).

| 에이전트 | 역할 | 권장 모델 | 도구 경계 |
|---|---|---|---|
| `spec-researcher` | 데이터시트·UG·IP 조사, 요구사항 정제 | opus | Read, Grep, WebFetch(사내 문서) |
| `microarch-designer` | 마이크로아키텍처·인터페이스·상태기계 설계, ADR 작성 | opus | Read, Write, Grep |
| `rtl-coder` | SystemVerilog/VHDL 구현 | sonnet | Read, Write, Edit, Bash |
| `testbench-engineer` | TB/UVM/cocotb·커버리지 작성 | sonnet | Read, Write, Edit, Bash |
| `lint-checker` | 린트·합성성·스타일 검토(**수정 안 함**) | sonnet | Read, Grep, Bash(lint) |
| `cdc-analyst` | 클록 도메인 크로싱·리셋 도메인 검토 | opus | Read, Grep, Bash(cdc) |
| `timing-constraints` | XDC 작성·STA 결과 해석 | opus | Read, Write, Bash(vivado) |
| `synthesis-runner` | 합성·구현 배치 실행·리포트 파싱 | sonnet | Read, Bash(vivado) |
| `verification-reviewer` | 검증 계획·커버리지·리그레션 리뷰(**수정 안 함**) | opus | Read, Grep, SendMessage |
| `rca-debugger` | 실패 리그레션/타이밍 위반 근본원인 분석 | opus | Read, Grep, Bash |

> **가드레일 예**: `lint-checker`·`verification-reviewer`는 `Write`/`Edit` 미부여 → 검증자는 판정만, 수정은 `rtl-coder`가. `synthesis-runner`의 `Bash`는 `vivado`·`verilator`로 화이트리스트(파괴적 명령 차단).

### 4.3 스킬 구성 (워크플로)

- **`rtl-generate-verify`** (생성-검증 + 재시도 상한): `rtl-coder`가 모듈을 생성 → `run-lint`/`run-sim`로 검증 → 실패 시 재작성, **`MAX_RETRIES=3` 후 사람에게 에스컬레이션**(참고: [`ex-08-15`](../ex-08-15-max-retries-code)). "테스트/린트를 우회하거나 비활성화해 통과시키지 않는다"를 규칙으로 못박음.
- **`rtl-review-team`** (팬아웃·팬인 오케스트레이션): 한 변경(diff)에 대해 `lint-checker`·`cdc-analyst`·`timing-constraints`·`verification-reviewer`를 **병렬**로 돌리고 `must-fix`/`should-fix`/`watch`로 통합(참고: [`ex-11-05`](../ex-11-05-orchestrator-6phase) 6 Phase, [`ex-06-12`](../ex-06-12-pr-review-skill-md) 통합 게이트).
- **`run-lint`/`run-sim`/`run-synth`** (실행 스킬): `bin/run.sh`가 실제 툴을 배치 호출하고 로그를 구조화(참고: [`ex-05-11`](../ex-05-11-with-without) 실행 스킬). 기본 **mock 모드**(툴 없이 산출 검증) + `USE_LIVE_TOOLS=1`에서 실제 EDA 호출(참고: [`ex-13-01`](../ex-13-01-dependency-mapper)의 mock/live).
- **`device-refs`** (라우터 + references): 요청이 UltraScale+냐 Versal이냐에 따라 `references/`를 조건부 로드(참고: [`ex-05-06`](../ex-05-06-domain-references)). 디바이스별 프리미티브·타이밍 특성 지식을 분리해 토큰 절약.

### 4.4 적용 아키텍처 패턴 (8장 매핑)

| 패턴 | RTL 적용 |
|---|---|
| 파이프라인 | 사양 → 설계 → RTL → 검증 → 합성의 순차 흐름 |
| 팬아웃·팬인 | 린트+CDC+타이밍+검증 병렬 리뷰 → 통합 리포트 |
| 전문가 풀(라우터) | 이슈 유형별(타이밍/CDC/린트) 전문 에이전트 분기 |
| 생성-검증 | RTL 생성 ↔ 시뮬/린트 검증 루프(재시도 상한) |
| 감독자 | 리그레션 실패 다수를 런타임에 분류·배분 |
| 계층적 위임 | 블록(top) → 서브모듈 → 리프 모듈 위임 |

### 4.5 하네스 자체 생성 — 메타스킬 활용

초기 하네스 골격은 **메타스킬**(참고: [`목차.md`](./목차.md) 「메타스킬 부연 설명」, `revfactory/harness`)로 도메인 설명("AMD FPGA RTL 팀 구성")을 받아 **에이전트·스킬·CLAUDE.md 초안을 자동 생성**한 뒤, RTL 전문가가 사내 규칙에 맞춰 다듬는 방식을 권장합니다. 이렇게 하면 구축 리드타임이 단축됩니다.

## 5. 구축 비용 (예시 산정 — 조직별 재산정 필요)

> 아래는 **가정에 기반한 예시**입니다. 실제 값은 인건비 단가·기존 EDA 라이선스 보유 현황·클라우드 정책에 따라 달라집니다.

### 5.1 구축(1회성) — 파일럿 12주 가정

| 항목 | 가정 | 예시 규모 |
|---|---|---|
| 인력(하네스 설계) | 시니어 RTL/검증 1인 × 12주(50%), AI 하네스 엔지니어 1인 × 12주 | 약 1.5 FTE·분기 |
| 하네스 저작 | 에이전트 10종 + 스킬 6종 + references 초안 | 상기 인력에 포함 |
| 파일럿 대상 | 중간 규모 IP 블록 1~2개(기존 검증셋 보유) | — |
| 교육/온보딩 | 팀 대상 워크숍 2~3회 | 소규모 |

### 5.2 운영(반복) — 모델 API 토큰

| 항목 | 가정 | 비고 |
|---|---|---|
| 모델 호출 | Claude(설계·검토 opus, 구현·실행 sonnet) — 직접 API 또는 Bedrock/Vertex 경유 | [`목차.md`](./목차.md) 「Claude 모델 접근 경로」 참고 |
| 토큰 절감 장치 | Progressive Disclosure(references 조건부 로드), mock 우선 | 상시 컨텍스트 축소 |
| 비용 통제 | 입력/출력 토큰 상한, 재시도 상한, dry-run 우선 | 폭주 방지 |

### 5.3 기존 자산 재활용(추가비용 최소)

- **EDA 툴 라이선스(Vivado/Vitis/시뮬레이터)**: 이미 보유한 경우 추가비용 없음. 하네스는 이를 **호출만** 함.
- **컴퓨팅**: 합성/시뮬 서버(온프레미스/클라우드)는 기존 것을 사용. 하네스는 배치 잡을 스케줄링.
- **오픈소스(Verilator/cocotb)**: 무료 — 린트·초기 시뮬을 저비용으로 병행.

> **총소유비용(TCO) 관점**: 최대 비용은 EDA 라이선스·컴퓨팅이며 이는 **기존 지출**입니다. 하네스가 추가하는 것은 **하네스 저작 인건비(1회성) + 모델 토큰(운영)** 이며, 뒤의 6절 효과로 상쇄를 노립니다.

## 6. 구축 효과

### 6.1 정성적 효과

- **재현성**: 조사·설계 근거·검증 절차가 파일(산출물)로 남아 리뷰·감사·재사용 가능.
- **일관성**: 코딩/리셋/CDC 규칙이 스킬로 고정 → 사람마다 다른 스타일·반복 린트 위반 감소.
- **지식 코드화**: 시니어의 판단 기준이 "실행 가능한 규칙(Why-First)"으로 이전 → 온보딩 단축.
- **조기 검증**: 린트·CDC·타이밍을 후반부가 아니라 **커밋 시점부터** 반복 점검 → 후반 재작업 감소.
- **안전성**: 검증자는 수정 권한이 없고, 자동 루프는 재시도 상한·에스컬레이션으로 통제.

### 6.2 정량 KPI (측정 프레임 — 목표치는 파일럿에서 설정)

본 저장소의 With/Without 실측 방식([`ex-05-11`](../ex-05-11-with-without))을 그대로 차용해 **하네스 유무 A/B**로 측정합니다.

| KPI | 측정 방법 | 방향 |
|---|---|---|
| 모듈 초안 리드타임 | 사양→린트 통과 RTL 초안까지 시간 | 단축 |
| 린트/CDC 위반 밀도 | KLOC당 위반 건수 | 감소 |
| 리그레션 실패 분류 시간 | 실패→원인 후보까지 시간(rca-debugger) | 단축 |
| 리뷰 커버리지 | 변경당 점검된 관점 수(린트/CDC/타이밍/검증) | 증가 |
| 재작업률 | 후반 단계에서 되돌아온 변경 비율 | 감소 |

> 목표 수치는 **파일럿 실측 후** 확정합니다(근거 없는 수치 제시 지양).

## 7. 구축 후 단계별 방법의 변화 (Before → After)

전체 흐름: **요구 정의 → 조사 → 설계 → 구현 → 검증 → 리뷰 → 배포 → 모니터링**(파이프라인). 각 단계에서 하네스가 무엇을 바꾸는지 정리합니다.

### 7.1 요구 정의(Requirements)
- **Before**: 요구·인터페이스·성능 목표가 구두·산발 문서로 흩어져 검증 기준이 모호.
- **After**: `spec-researcher`가 요구를 **검증 가능한 항목**(기능/성능/타이밍/자원 예산)으로 정제하고, 각 요구에 **수용 기준(acceptance)** 과 추적 ID를 부여해 파일로 고정. 이후 검증·리뷰가 이 ID를 참조.

### 7.2 조사(Research)
- **Before**: 데이터시트·UG(User Guide)·기존 IP를 개인이 산발 조사, 결과가 휘발.
- **After**: `spec-researcher`가 `device-refs`(UltraScale+/Versal 분기)와 사내 문서를 근거로 프리미티브·제약·재사용 IP를 조사해 **출처와 함께** 산출물로 남김.

### 7.3 설계(Design)
- **Before**: 마이크로아키텍처 결정의 대안·근거가 문서화되지 않음.
- **After**: `microarch-designer`가 인터페이스·상태기계·클록/리셋 도메인·자원 추정과 **결정 근거(ADR)** 를 파일로 산출 → 요구 ID에 매핑, 리뷰·재사용 용이.

### 7.4 구현(Implementation)
- **Before**: 스타일·리셋/CDC 규칙이 사람마다 다름, 린트 위반 반복.
- **After**: `rtl-coder`가 스킬의 코딩 규칙(Why-First)에 따라 구현 → `rtl-generate-verify` 루프가 린트·시뮬을 통과할 때까지 반복(상한 내), 실패 시 사람에게 에스컬레이션.

### 7.5 검증(Verification)
- **Before**: TB/커버리지 작성 병목, 리그레션 실패 수동 분류.
- **After**: `testbench-engineer`가 TB 초안·커버리지 포인트를 요구 ID 기준으로 생성, 리그레션을 배치 실행. `rca-debugger`가 실패 **1차 분류**(사람은 확정만).

### 7.6 리뷰(Review)
- **Before**: 리뷰가 리뷰어 가용성·개인 경험에 좌우되고 점검 관점이 누락됨.
- **After**: `rtl-review-team` 스킬이 변경(diff)마다 `lint-checker`·`cdc-analyst`·`timing-constraints`·`verification-reviewer`를 **병렬(팬아웃·팬인)** 로 돌려 `must-fix`/`should-fix`/`watch`로 통합. 검증자는 **수정 권한 없이 판정만**, 수정은 `rtl-coder`가 반영. 최종 승인은 사람.

### 7.7 배포(Deploy — 비트스트림/릴리스)
- **Before**: 합성·타이밍 클로저·비트스트림 생성이 수작업 스크립트로 산발.
- **After**: `run-synth` 스킬이 Vivado Tcl 배치를 표준 절차로 실행하고 타이밍/자원 리포트를 구조화. **사인오프(합성 결과·타이밍 서명)와 실제 배포 승인은 사람이 최종 결정** — 하네스는 준비·요약까지.

### 7.8 모니터링(Monitoring)
- **Before**: 릴리스 후 회귀·필드 이슈가 다음 프로젝트로 피드백되지 않아 같은 실수가 반복.
- **After**: 리그레션·타이밍 마진·자원 사용률·필드 리포트를 **추세로 관측**하고, 회귀 발생 시 `rca-debugger`가 근본 원인을 분석([Post-mortem/blameless](./목차.md#post-mortem-부연-설명)). 개선점은 **하네스 규칙·references·에이전트로 환류**되어(10장 진화 루프) 다음 사이클의 품질을 올림.

> **불변 원칙**: 최종 기능/타이밍 사인오프, 실제 하드웨어 배포 승인은 **사람이 담당**합니다. 하네스는 자동 승인·자동 릴리스를 하지 않습니다(검증자 무수정·자동 커밋 금지 원칙과 동일).

## 8. 개발 인력·조직 변화

### 8.1 역할의 이동 (대체가 아니라 재배치)

| 기존 역할 | 변화 방향 |
|---|---|
| RTL 설계자 | 반복 코딩 비중 ↓ → **아키텍처 결정·리뷰·하네스 규칙 저작** 비중 ↑ |
| 검증 엔지니어 | TB 뼈대 작성 ↓ → **검증 전략·커버리지 클로저·실패 확정** 비중 ↑ |
| 시니어/리드 | 개별 지시 ↓ → **하네스(규칙·에이전트) 관리자**, 지식의 코드화 담당 |
| 신규/주니어 | 하네스가 가드레일 → **온보딩 가속**, 규칙 안에서 안전하게 기여 |

### 8.2 신설·강화 역할

- **하네스 스튜어드(Harness Steward)**: 에이전트·스킬·references·CLAUDE.md를 관리하고 **하네스를 진화**시키는 역할(10장 "하네스 등록과 진화", Phase 0 감사 / 운영 루프). 소규모 팀은 겸직 가능.
- **AI/EDA 통합 담당**: 툴 배치 스크립트·CI 연동·토큰 비용 관리.

### 8.3 조직 운영 원칙

- **동시 활성 에이전트 3~5명 권장**(참고: 12장 Phase 활성 매트릭스 [`ex-12-03`](../ex-12-03-team-8-agents)) — 무분별한 에이전트 증식 경계(6장 "292개 에이전트 사건").
- **하네스는 버전 관리·리뷰 대상**: 규칙 변경도 코드 리뷰를 거침(drift 방지, ADR 기록).

## 11. 결론

AMD FPGA RTL 개발은 툴 체인이 스크립트 친화적이고 검증이 반복적이라 **하네스 효과가 큰 도메인**입니다. 본 제안은 본 저장소가 검증한 패턴(에이전트·스킬·오케스트레이터, 6 아키텍처 패턴, 생성-검증 + 재시도 상한·에스컬레이션, 도메인 분기 references, 메타스킬)을 RTL 도메인에 매핑해, **요구 정의~모니터링 전 단계를 재현 가능한 파이프라인으로 표준화**합니다. EDA 라이선스·컴퓨팅은 기존 자산을 재활용하므로 추가 비용은 하네스 저작(1회성)과 모델 토큰(운영)에 국한되며, 파일럿 A/B로 효과를 정량 검증한 뒤 확산하는 **저위험 단계적 도입**을 권장합니다.
