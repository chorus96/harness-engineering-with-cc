> 이 문서는 저장소에 담긴 22개 실습 예제를 분석·정리한 것입니다.
> 원서: 한민호 저, **《하네스엔지니어링 with Claude Code》** (한빛미디어).
> 각 예제 폴더의 `README.md`, `.claude/agents/*.md`, `.claude/skills/*/SKILL.md`, `CLAUDE.md` 를 근거로 작성했습니다.

---

## 1. 하네스 엔지니어링이란

이 책의 핵심 주장은 Claude Code를 **"한 번의 대화를 잘 굴리는 도구"가 아니라 "작업 환경(=하네스)을 미리 세팅해두는 도구"** 로 다루자는 것입니다. 같은 한 줄 프롬프트라도 **전문 에이전트 + 스킬 + 규칙(CLAUDE.md)** 을 먼저 깔아두면 산출물의 품질·구조·재사용성이 체계적으로 달라집니다.

하네스는 세 가지 구성 요소로 이루어집니다.

| 구성 요소 | 위치 | 역할 |
|---|---|---|
| **에이전트(agent)** | `.claude/agents/*.md` | 특정 역할·도구·모델로 고정된 서브에이전트 정의 |
| **스킬(skill)** | `.claude/skills/<name>/SKILL.md` | 자연어 트리거로 호출되는 재사용 워크플로 |
| **프로젝트 규칙** | `CLAUDE.md` | 오케스트레이션 포인터·공통 규칙 |

## 2. 공통 구조 패턴

거의 모든 예제가 아래 프론트매터 필드로 에이전트/스킬의 **경계를 물리적으로 강제**합니다.

### 에이전트 프론트매터
```yaml
---
name: security-analyst           # 호출 식별자
description: ...                  # 언제/무엇을/어떤 기준으로 (자연어 트리거)
model: sonnet | opus             # 작업 난이도에 맞춘 모델 선택
tools: Read, Grep, Glob, Bash    # 허용 도구 화이트리스트 (미기재 시 부모 상속)
---
```

### 스킬 프론트매터
```yaml
---
name: commit-message
description: "... '커밋 메시지' 같은 자연어 요청 시 반드시 사용. 단, ~는 아니다."
allowed-tools: Bash Read Write
---
```

핵심 설계 원칙 세 가지가 예제 전반에 반복됩니다.

- **도구 경계(tool boundary)**: `tools`/`allowed-tools` 에서 `Write`·`Edit`·`Bash` 를 의도적으로 빼서 "읽기 전용", "검증만", "수정만" 같은 역할을 물리적으로 고정.
- **모델 티어링**: 판단·설계는 `opus`, 기계적 실행·정형 산출은 `sonnet` 으로 배분.
- **dry-run / mock 우선**: LLM 비용 0으로 산출을 검증할 수 있게 `wc`·`grep`·스텁으로 실측하고, 실제 LLM 판정은 설계 명세대로 예상치를 기록.

## 3. 장별 예제 분석

### 2장 — 첫 하네스

#### `ex-02-01-ab-comparison` — 하네스 적용 전/후 A/B 비교
동일한 한 줄 프롬프트 `claude code 사용 팁 정리해주세요` 를 **맨몸(non-harness)** 과 **하네스 적용(apply-harness)** 두 방식으로 실행해 산출물을 2단 페이지(`index.html`)로 비교합니다.

- **A. 미적용**: 자유 형식 치트시트 1개, 예시·출처 없음, 1회성.
- **B. 적용**: 전용 에이전트 3종(`tip-researcher`/`tip-writer`/`tip-curator`) + 공유 스킬 3종(`tip-collect`/`tip-format`/`tip-publish`) 으로 "상황 → 방법 → 예시 → 주의점" 표준 포맷 8편 + 인덱스 산출.

> **결론**: 유일한 차이는 "작업 전에 하네스를 깔아두었는가" 뿐인데, 품질·구조·재사용성이 체계적으로 갈린다.

#### `ex-02-02-my-first-harness` — 2인 팀 커밋 메시지 (최소 하네스)
가장 작은 완결형 하네스. `commit-message` 스킬이 두 에이전트를 **순차 호출**해 Conventional Commits 메시지를 생성합니다.

- `commit-msg-author` (sonnet, `Bash/Read/Write`): `git diff --cached` + `git log -10` 을 읽어 초안을 `_workspace/commit-draft.md` 에 작성.
- `commit-msg-reviewer` (sonnet, `Read/Bash/Write`): 형식·diff 사실 일치를 검증해 `PASS/REDO` 판정.
- 스킬 워크플로: **Precondition 체크 → author → reviewer → PASS/REDO 분기 → 최대 2회 재호출 후 종료** (무한 루프 방지 안전장치).

핵심 교훈: 생성자와 검증자를 분리하고, 중간 산출물을 `_workspace/` 로 넘기는 **생성-검증(generator-verifier) 루프** 의 원형.

### 4장 — 에이전트 설계

#### `ex-04-01-security-analyst` — 읽기 전용 보안 분석 에이전트
`security-analyst` (sonnet, `Read/Grep/Glob/Bash`). **`Write`/`Edit` 를 의도적으로 제외**해 수정 권한을 물리적으로 차단한 것이 핵심입니다.

- 취약점을 심은 Flask 샘플 앱(`sample-app/app.py`, `db.py`)에 적용.
- 산출: 위치(파일:라인) · 설명 · 권장 수정안 · **Critical/High/Medium/Low 4단계 심각도**, 가능하면 OWASP Top 10 / CWE 매핑.
- Bash 는 `grep/find/cat` 같은 읽기 전용 조회로만 사용 — 도구는 줬지만 사용 규칙으로 재차 좁힘.

#### `ex-04-02-copy-editor` — 기계적 교정 1단계 에이전트
`copy-editor` (opus). **딱 3종의 기계적 교정** 만 수행하고 판단이 필요한 윤문은 하지 않도록 경계를 명시합니다.

- 교정 3종: 산문 끝 콜론 제거 / Bold 한글 조사 위반 / 명백한 오탈자.
- **예외 케이스** 를 명시적으로 나열(`12:30`, 코드 블록 `key: value`, 표 헤더) → "수정하지 않는다" 섹션으로 오버리치 방지.
- 모호하면 직접 고치지 않고 **보류 항목** 으로 보고, diff 단위는 작게.
- `tools` 필드는 원문에 없어 부모 도구를 상속(Read/Edit) — 프론트매터 주석에 그 근거를 남긴 점이 특징.

**대표 코드 — `sql-query` 라우터 패턴** (`ex-05-06`): SKILL.md 본문은 도메인 내용을 담지 않고 조건부 링크만 둔다.
```
## 라우팅
- 매출 관련 요청이면 → references/finance.md
- 재고 관련 요청이면 → references/inventory.md
단순 SELECT는 직접 작성. 도메인 템플릿이 필요할 때만 해당 references를 로드한다.
```

**대표 코드 — Why-First 규칙** (`ex-05-11` csv-summary): 규칙마다 "왜냐하면" 이유를 붙인다.
```
- 숫자 열만 평균/중앙값/표준편차를 낸다 — 왜냐하면 문자열 열에 통계는 의미가 없기 때문.
- 그룹 요청이면 GROUP BY 후 집계 — 왜냐하면 전체 평균은 부서 비교에 쓸 수 없기 때문.
```
이 스킬은 실제로 동작하는 미니 구현(`bin/run.sh`, 파이썬 stdlib `csv`·`statistics` 만 사용)을 함께 제공합니다.

### 6장 — PR 리뷰 오케스트레이션

#### `ex-06-12-pr-review-skill-md` — `pr-review-orchestrator` SKILL.md 실물
책의 SKILL.md 전문을 보존한 예제. **오케스트레이터는 코드를 직접 고치지 않고**, 팀을 만들고 작업 큐를 배치하고 팀원 간 직접 메시지를 허용한 뒤 최종 리포트만 통합합니다.

- **Phase 0~5** 워크플로: 사전조건 → `TeamCreate` + 팀원 4인 → `TaskCreate` 4작업(마지막 `integrate` 는 `depends_on` 으로 앞 3작업 대기) → **팀원 간 `SendMessage`(리더 미경유)** → 통합 게이트 → 종료(`TeamDelete`).
- 팀원 간 메시지 형식을 JSON(`type/severity/file/line/claim/request`)으로 **고정**.
- 최종 리포트는 `must-fix`/`should-fix`/`watch` 3섹션만. 파일 40개 초과 시 위험도 높은 묶음만 리뷰하는 방어 규칙 포함.

#### `ex-06-15-292-agent-incident` — 292개 에이전트 사건 (정량 검증)
채널 수 폭주 사례를 **책 인용 + 정량 데이터 + 외부 자료 교차 검증** 메모로 정리한 사례 노트. 코드보다 "무분별한 에이전트 증식의 비용"을 데이터로 뒷받침하는 문서형 예제.

### 8장 — 안전장치

#### `ex-08-15-max-retries-code` — `MAX_RETRIES` 실행 가능 코드
책 p140 의사코드 시그니처를 그대로 보존하되, 더미 `CodeGenerator`/`TestRunner` 로 **실제 실행이 가능한** 파이썬 스텁(stdlib만).

```python
MAX_RETRIES = 3
def generate_with_retries(spec, generator, verifier):
    for attempt in range(MAX_RETRIES):
        artifact = generator.run(spec)
        result = verifier.run(artifact)
        if result.passed:
            return artifact
    return f"escalated: {MAX_RETRIES}회 실패, 수동 개입 필요"
```
- `python3 run/max_retries.py success` → 2회차 PASS.
- `python3 run/max_retries.py fail` → 3회 실패 후 **escalate(수동 개입)**.

핵심 교훈: 생성-검증 루프에는 반드시 **재시도 상한 + 에스컬레이션 경로** 를 둔다.

### 11장 — 코드 리뷰 팀

한 PR을 여러 렌즈로 검토하는 **4인 리뷰어 팀** 을 점진적으로 조립합니다.

#### `ex-11-03-static-analyzer-md` — `static-analyzer` 에이전트 + 샘플 TS PR
정적 이슈를 심은 TS PR과 `static-analyzer.md` 를 보존. **mock 모드 기본** + `tsc`·`eslint` 화이트리스트로 도구 경계를 강제합니다.

#### `ex-11-04-three-frontmatter` — 3 에이전트 frontmatter 공존
`static-analyzer`(복사) + 신규 3인으로 4인 팀 디렉토리를 구성. **도구 경계를 frontmatter로 강제** 한 것이 관전 포인트입니다.

| 에이전트 | 모델 | 도구 경계 |
|---|---|---|
| `security-auditor` | sonnet | — |
| `design-reviewer` | opus | **Bash 없음** (읽고 비교만) |
| `refactorer` | opus | `Read/Grep/Glob/Edit` — **Edit 단독**, 자동 커밋 금지, 생성-검증 3회 상한 |

#### `ex-11-05-orchestrator-6phase` — `code-review-team` 6 Phase
책 의사코드를 SKILL.md로 마감. `allowed-tools` 에 `TeamCreate/AgentTool/TaskCreate/SendMessage/TeamDelete` + `Bash(gh pr diff, gh pr comment)` 처럼 **인자 수준 화이트리스트** 를 지정한 점이 특징.

- **공식 5종 도구** vs **의사 함수 4종**(`parseDiff`/`waitForTeamCompletion`/`mergeReports`/`$`)을 명확히 구분해 "구현자가 직접 만들 부분"을 표시.
- **리더 무발화 원칙**: 리뷰 본문 텍스트는 워커 4인이 생산, 오케스트레이터는 호출·통합만. `gh pr comment` 까지만 하고 `git commit`·`gh pr merge` 는 호출 금지.

#### `ex-11-06-jwt-pr-bugs` — 의도 버그 4종 + 4인 팀 (mock)
JWT 리프레시 PR(5파일 ~300줄)에 **SQL 인젝션·N+1·경계면 불일치·테스트 0건** 4버그를 `INTENT_BUG_` 마커로 심고, mock 4 리뷰어를 적용해 **4×4 발견 매트릭스** 와 **Without/With 비교** 를 산출합니다.

- `mock`(기본, LLM 호출 0) / `live`(`EX_11_06_MODE=live`, 입력·출력 5k 토큰 상한) 두 모드.
- `grep -rn "INTENT_BUG_"` 로 심은 버그를 검증 가능하게 설계.

### 12장 — 풀스택 팀

#### `ex-12-03-team-8-agents` — 8 에이전트 + Phase 활성 매트릭스
로그인 기능을 8 에이전트로 개발하는 팀. 모델·도구 경계를 frontmatter로 강제하고, **Phase별 동시 활성 ≤ 4명** 을 매트릭스로 관리합니다.

| 에이전트 | 모델 | 도구 | 활성 Phase |
|---|---|---|---|
| `feature-pm` | opus | Team/Task/Agent/SendMessage 등 | 전 Phase (PM) |
| `api-designer` | opus | Read/Write/Grep/SendMessage | 1 |
| `ui-designer` | opus | Read/Write/Grep/SendMessage | 1 |
| `db-migrator` | opus | Read/Write/Grep/SendMessage | 1 |
| `backend-impl` | sonnet | Read/Write/Edit/Bash/SendMessage | 2,3 |
| `frontend-impl` | sonnet | Read/Write/Edit/Bash/SendMessage | 2,3 |
| `boundary-verifier` | opus | Read/Grep/SendMessage (**수정 없음**) | 2,3 |

### 13장 — 의존성 분석

#### `ex-13-01-dependency-mapper` — 의존성 그래프 → 결정론적 배치 계획
`dependency-mapper` (sonnet, `Read/Grep/Bash`) 가 `sample-src/` 의 import 그래프를 분석해 **위상정렬** 결과를 `batches.json` 으로 산출합니다.

- 절차: glob 수집 → import 추출 → **복잡도 = (size/100) + (imports×2) + (functions×3)** → 배치당 10~50 파일로 클러스터링 → 위상정렬(순환 시 한 배치로 묶고 `warning: "cyclic"`) → JSON 반환.
- **저장은 오케스트레이터, 변환은 하지 않음** — 에이전트는 초안(batches.json)만 반환하는 역할 분리.
- 기본 mock(`bash mock-mapper.sh`, LLM 비용 0), `USE_LIVE_LLM=1` 에서 실제 sonnet 호출. 순환(`cyclic-a/b.jsx`)·독립(`standalone.jsx`)·파싱 실패(`truncated.jsx`, `manual-queue` 기록) 케이스를 sample-src로 함께 제공.

## 4. 예제를 관통하는 핵심 패턴

1. **도구 경계로 역할을 물리적으로 고정한다.** 읽기 전용은 `Write/Edit` 제거(`security-analyst`, `dependency-mapper`, `reviewer`), 검증자는 수정 도구 없이 판정만(`boundary-verifier`), 리팩토러는 `Edit` 단독. description 으로 "무엇을 안 한다"까지 명시한다.

2. **모델을 작업 난이도에 맞춰 티어링한다.** 설계·판단·경계 검증은 `opus`, 정형 산출·구현·테스트는 `sonnet`.

3. **생성-검증 루프 + 재시도 상한 + 에스컬레이션.** author↔reviewer(2회), refactorer(3회), `MAX_RETRIES=3` 후 수동 개입.

4. **오케스트레이터는 직접 쓰지 않는다.** 팀을 만들고 작업을 배치하고 통합만 — 본문은 워커가 생산(리더 무발화). 팀원 간 `SendMessage` 는 리더를 거치지 않는다.

5. **SKILL.md는 라우터, 본문은 references로 위임.** 조건부 로드로 컨텍스트 절약(`sql-query` 메뉴판 패턴, book-writer 다중 모드).

6. **규칙에는 이유를 붙인다(Why-First).** "왜냐하면 …" 을 규칙 옆에 둔다.

7. **dry-run / mock 우선으로 비용 없이 검증한다.** 구조는 `wc`·`grep` 실측, LLM 판정은 명세대로 예상. 실제 호출은 `USE_LIVE_LLM=1`·`EX_..._MODE=live` 같은 환경변수 뒤에 둔다.

8. **의도된 결함을 심어 검증 가능하게 만든다.** `INTENT_BUG_` 마커, 취약점 심은 샘플 앱, 순환/파싱실패 fixture — grep 으로 재현·검증한다.
